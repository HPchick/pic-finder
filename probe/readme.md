# 技术栈验证说明

本目录用于验证 PySide6 技术栈能否承载 PIC FINDER 的界面需求，并实测两项打包指标。

本目录所有内容都是一次性验证代码，不属于正式实现。验证完成后应当删除，并把结论回填到 `docs/design-decisions.md` 的 DD-06 与 DD-20，以及 `docs/introduction.md` 的 N-01 与 N-07。

## 验证什么

本验证回答四个问题。

1. PySide6 能否做出三页切换加缩略图图墙的结构。
2. 三页同时构建时，冷启动耗时能否满足 N-01 的 3 秒要求。
3. PyInstaller 目录模式打包后，程序目录体积是多少。
4. Qt 的列表控件在 2 万条占位数据下是否仍然流畅。

## 前置条件

本机需要具备下列条件。

- Python 3.11 及以上，本机已装 3.13.15。
- PySide6，执行 `python -m pip install PySide6` 安装。
- PyInstaller，执行 `python -m pip install pyinstaller` 安装。`build-and-measure.ps1` 会在缺失时自动安装。

**版本要求。** Python 3.13 自 PySide6 6.8.1 起获得支持，官方发行说明写明 6.8.1 加入 Python 3.13。当前 PyPI 上的版本同时支持 3.13 与 3.14，因此直接安装最新版即可。不要锁定到 6.8.0，该版本在 Python 3.13 上有已知的安装问题。

**注意。** 开发机的命令执行环境没有网络出口，无法从 PyPI 安装依赖。因此本验证必须在能访问国内镜像的环境中执行，例如：

```
python -m pip install PySide6 pyinstaller httpx -i https://pypi.tuna.tsinghua.edu.cn/simple
```

## 怎么跑

在 `pic-finder` 目录下执行。

```
powershell -ExecutionPolicy Bypass -File probe\build-and-measure.ps1
```

本机装有 Windows PowerShell 5.1，没有 PowerShell 7，因此上面用 `powershell` 而不是 `pwsh`。脚本也与 PowerShell 7 兼容。

脚本会依次完成四步：检查环境、打包、测量体积、启动五次并记录耗时。

### 一处必须遵守的编码约束

`build-and-measure.ps1` **只能包含 ASCII 字符**。

原因是 Windows PowerShell 5.1 读取没有字节顺序标记的脚本时按 ANSI 解码。中文会因此损坏，脚本直接语法报错。因此所有中文提示语都放在 `messages.json` 里，由脚本以 UTF-8 显式读取。

若要修改脚本的提示文字，改 `messages.json`，不要往脚本里写中文。

## 看什么

脚本结束时在屏幕上给出汇总，并写入 `probe/probe-result.json`。

需要回报的两项数值如下。

| 字段 | 含义 | 用于回填 |
|---|---|---|
| `size_mb` | 打包后程序目录的总体积 | N-07 |
| `startup_window_average` | 从进程创建到窗口出现的平均耗时，这是用户感知的冷启动 | N-01 |

`startup_frame_average` 是进程内首次绘制的耗时，它不含进程创建与动态库加载，因此小于上一项，仅供定位问题使用。

## 冷启动的口径

N-01 要求的是「打包后实机测量」，因此口径必须是**从进程创建到窗口出现**，即用户双击图标后等待的时间。

这个计时必须在 `Start-Process` 之前开始，不能用被测程序内部的计时器。原因是被测程序启动时，进程创建与 Qt 动态库加载已经发生完了，那一段恰恰是 Windows 上最耗时的部分。

`build-and-measure.ps1` 采用外部计时，并轮询进度 `MainWindowHandle` 以取得窗口真正出现的时刻。

**一条限制。** 窗口句柄只在交互式桌面会话中出现。如果脚本在无桌面的会话里运行，窗口时间会取不到，此时脚本会明确提示，不会写入 0。

## 判定标准

| 指标 | 目标 | 处理 |
|---|---|---|
| 冷启动 | 不超过 3 000 ms | 达标则确认 N-01。超标则先改为按需创建页面 |
| 体积 | 无硬性上限，见 DD-20 | 如实记录，不作判定 |

若冷启动超标，第一项优化是把三个页面改为首次切换时才创建，而不是启动时全部构建。本验证程序故意在启动时构建三页，测的是最坏情况。

## 已跑过的结果

| 项 | 结果 | 状态 |
|---|---|---|
| 依赖安装 | Python 3.13.15、PySide6 6.11.2、PyInstaller 6.22.3、httpx 0.28.1 | 完成 |
| 程序目录体积 | 110.2 MB | 完成，回填 N-07 |
| 界面可用性 | 三页切换与图墙在实机正常 | 完成 |
| 冷启动数值 | 首次测量取到无效值 | 开发者已主观确认够快，暂不补测 |

首次测量取得无效值的原因有两条，已修正，记录于此以免重复踩坑。

1. 使用了 `firstFrameSwapped` 事件计数而没有兜底。该事件不触发时写入空值，外部脚本把空值记为 0，看起来像「0 毫秒」。
2. 计时从进程内部开始，漏掉了进程创建与动态库加载。这一段才是用户在 Windows 上真正等待的部分。

修正内容：口径改为外部计时，事件计数保留但增加兜底闹钟，并记录事件的来源以便判断哪条路径生效。

## 还可以顺手验证什么

下列事项与界面无关，但同一次环境里可以一并执行，避免再来一轮。

1. Danbooru 接口的连通性与实际返回字段。
2. Openverse 匿名额度，以及中文关键词的检索质量。
3. 大都会艺术博物馆接口的具体参数。
4. WD14 Tagger 各版本的实际文件体积与单张推理耗时。

这四项的结论回填到 `docs/feasibility.md` 与 `docs/source-candidates.md` 的待实测清单。
