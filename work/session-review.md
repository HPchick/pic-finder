## 四、踩过的坑与教训

### 4.1 环境陷阱（本会话至少各踩过一次）

1. **打包必须提权**（PyInstaller 要开命名管道，受限模式禁止）。命令：`installer\build.ps1 -Zip` 然后 `installer\make-installer.ps1`。**永远不要加 `-Clean`** —— 用户会把便携包解压到 `installer/dist/` 并在里面运行，`-Clean` 会连他正在跑的那份一起删。0.1.3 那次 `-Clean` 因文件占用失败，**反而救了用户的副本**。
2. **终端中文全是乱码，且 PowerShell 的管道抓不到原生程序输出**（`| Out-File`、`| Select-Object` 报 `Access is denied`）。一律让脚本把结果写进 `work/_xxx.txt`，再用 read 工具读。
3. **测试不能用 `tempfile`**：沙箱会把平台临时目录重定向，那里能建文件却删不掉，`TemporaryDirectory` 清理时报 `WinError 5`（14 条用例整片变红，看起来像路径层有 bug）。用 `tests/.scratch`（`tests/scratch.py`）。
4. **`.ps1` / `.iss` / `.bat` 必须纯 ASCII**：Windows PowerShell 5.1 读取无 BOM 的脚本时按 ANSI 解码，中文直接导致语法报错。中文提示外置到 `installer/messages.json` 并按 UTF-8 显式读取。**本会话踩了两次**（probe 测量脚本、`verify.ps1` 里的正则）。
5. **BOM 双向坑**：`Set-Content -Encoding UTF8` 在 PS 5.1 下会写 BOM，Python 读不了；用 edit 工具改 `.ps1` 会剥掉 BOM 且容易顺手写进中文注释。写 Python 用 read/write 工具，改 `.ps1` 一律检查非 ASCII 字节数。
6. **离屏跑界面**：`QT_QPA_PLATFORM=offscreen`、`QT_QPA_FONTDIR=C:\Windows\Fonts`、`PYTHONPATH=<repo>\src`。`QApplication` 必须先于 `QPixmap` 创建（否则 `QPixmap: Must construct a QGuiApplication before a QPixmap`，探针以 `-1073740791` 崩溃）。
7. **改完 `db` 的 seed SQL 一定要跑一次 `--data-root` 冒烟**。本会话在 `SEED_SITES_SQL` 末尾漏了一个分号 → `executescript` 抛 `OperationalError: incomplete input` → 启动直接失败；而失败路径会弹 `QMessageBox.critical`，**离屏模式下模态框永远等不到人点，冒烟就挂死了五分钟**。这是最有价值的一条。
8. **网络真相**：Python/httpx 有出口；`github.com`、`huggingface.co`、`raw.githubusercontent.com` 解析到本机代理（MITM），certifi 校验失败但 `verify=False` 可用——**早前文档里「huggingface 不可达」的结论是错的**。网络会抖（同一批里首页超时但接口 200，DNS 也换过 IP），**一律加重试**。
9. **Qt 在本机无法建立任何 HTTPS 连接**（它用 Windows 安全通道做 TLS；明文 HTTP 到百度成功，HTTPS 连国内站都失败）。所有网络代码必须走 httpx。`QPixmap` 只能在主线程创建，`QImage` 可以跨线程。
10. **信号到信号必须 `a.signal.connect(b.signal)`，绝不能 `connect(b.signal.emit)`**——把信号当普通方法连之后，事件被投递到工作线程自己的队列，转发时那个线程已准备退出，事件就没了。**单元测试抓不到（测试里没有事件循环），只在真机出现。** 判据：给引擎回调与界面槽各加一行日志，前者有输出而后者没有，就是这条。
11. **`card.setParent(None)` 在 Qt 里等于把控件变成顶层窗口**，Windows 会真的建一个原生窗口再隐藏——清一页 200 张卡片就闪 200 下。只能用 `hide()` + `deleteLater()`。
12. **`QLabel` + `setWordWrap(True)` 遇上无空格长路径**会把长串压成一列窄条：控件里 `text()` 是对的，**只有肉眼可见处是错的**（显示成 `D:`）。**看不见界面就不能靠读代码判断界面**，用 `work/shot_wizard.py` 那类截图脚本核对。
13. **`.ui` 的 `item` 不支持逐项 stretch**（uic 报 `Unexpected attribute stretch`；`layoutStretch`/`stretch` 两个拼法都生成废代码）→ 用 Designer 原生的 `sizePolicy=Expanding`。另外 `findChild` 名字对不上**不报错**，返回 `None`，按钮点了没反应。
14. **`Start-Process -ArgumentList` 不替你加引号**：中文检索词 `站姿 侧视` 被拆成两个参数，argparse 以**状态码 2** 退出、日志一个字都没写——看起来和「打包坏了」一模一样，实际是测试脚本的错。**静默安装必须重定向输出**，否则安装程序写满继承来的管道就卡住（五分钟没反应、一个文件都没建）。
15. **子代理实测直接推翻了两条既有假设**：`client.py` 的 `MAX_PAGES=20` 让 Danbooru 只取 4000 张（丢掉 98%）；`docs/feasibility.md` 记的 yande.re「limit 上限 100」实测是 1000。各站门道：Danbooru `page` ≤1000（1001 起返回 410 `You cannot go beyond page 1000.`）；Safebooru `pid` 从 0 起、越界返回 **HTTP 200 + XML `Search error: API limited due to abuse.`**（不是 429，极易误判成功）；yande.re/Konachan `limit` ≤1000、无页数上限、返回 `{"posts":[...]}`；`konachan.com` 一律 403 Cloudflare，`konachan.net` 同接口可用；Openverse 匿名深度硬上限 240；Gelbooru 一律 401（要真密钥）。

### 4.2 判断错误与返工原因

1. **`INSERT OR IGNORE` 会同时吞掉两类完全不同的情况**：重复写入（正常）与违反约束（错误），混在一起会让计数差额永远说不清。一律改成显式唯一键探测；**报告里的每个数字都要与库里的真实查询对账**（正是靠对账才发现 `common` 那个设计漏洞；只核对「退出码为 0」会漏掉它）。
2. **测试失败先怀疑测试自己的假设**：本会话有两条用例连续失败两次，两次都是助手对「某个标签是否存在」的假设错了（`standin` 与 `stand` 都是 Danbooru 真实标签），被验证的代码一直是对的。
3. **「所有指标都正常，但双击没反应」**：打包入口指向 `picfinder/__main__.py`，PyInstaller 把入口当顶层脚本执行 → `__package__` 为空 → 相对导入失败。**最阴的地方是体积比修好后小 5 MB**（入口在导入阶段就崩，PyInstaller 的分析根本没看到 `sqlite3`、`httpx`、`certifi`）。抓到它靠 `verify.ps1`，且必须用 `Start-Process -Wait -PassThru`（窗口模式程序不会让调用运算符等待，`$LASTEXITCODE` 取到空值，看起来像正常退出）。
4. **「算得对不等于算得及时」**：只重写 `resizeEvent` 不足以跟上滚动区可用宽度的变化——图墙自身没变大时，滚动区内部可用宽度照样会因为侧栏出现、滚动条消失而改变，而这种变化不触发图墙的 `resizeEvent`。修法是给滚动区视口装事件过滤器。同一个坑踩了两轮。
5. **性能问题的归因要先取证**：缩略图慢的真原因是「每张图新建一个 HTTP 连接」（握手比传输还久）+「一次失败就永久拉黑」，**不是单线程**。
6. **退出挂死**：`ThumbnailCache._pool` / `LibraryWall._decoder` 从不关闭 → 日志 17 秒写完而命令跑了 **408 秒**（大检索后关窗，进程为了排完缩略图队列多活好几分钟）。接 `closeEvent` **和** `application.aboutToQuit` 两条路（探针走的是 `application.quit()`，只接 `closeEvent` 不够）。
7. **孤儿文件**：两件作品发布同字节的图时，第二张文件已落盘而记录写不进（撞 `file_hash` 唯一索引）→ 留下不被索引的孤儿文件。修法是落盘前再查一次本地哈希 + 写库失败时删掉刚落盘的文件。这个漏洞是**写测试时撞出来的**，所以下载层用替身接口的离线测试很值。
8. **并发写入**：两个下载线程同时写同一个标签，`SELECT` 再 `INSERT` 不是原子的 → 撞唯一约束 → 整张图被判下载失败 → 重试又撞作品编号约束 → 最后变成「跳过」，用户会少一张图且不知道原因。改 `ON CONFLICT DO NOTHING` + 回查。
9. **索引装载的性能代价**：加了 10 MB 中文标签表后测试套件从 0.15 秒涨到 33 秒（每条用例重建索引）→ 用 `shared_index()` 进程级缓存。
10. **给无依赖环境写代码的顺序**：先把「不依赖第三方库」的两块（数据库表结构、词典格式）做掉，等依赖就位再写界面与网络——这是用户在依赖装不上时定的路线，执行得通。

## 五、值得警惕的地方

**按严重程度排。这一节是给下一任最重要的部分。**

### 5.1 最严重：把结论留在思维链里没有输出

「真机伶」映射问题的完整分析（CSV 原文、五档匹配逐档为什么落空、`_dice = 0.257`、影响面 22665 条 / 20047 条、三条根因、倾向的修复方向）**全部写在 reasoning 里，对话正文一个字都没有**。用户在两轮之后不得不把它整段贴回来，并说：

> 「这是你上上上轮的输出结果，**不知道为什么你全放思维链里了并没有输出，所以你不知道**」

**推论**：reasoning 不是交付物。凡是用户要的结论、诊断、数据，必须落到 text 里；「我在思维链里已经想清楚了」等于没做。这条直接造成了一整轮的返工与一次用户的信任摩擦。

### 5.2 把「图片标题」理解成数据库的 `title` 字段

用户说「分类依据直接读取图片标题」，助手去读数据库 `title` 字段（实测 100% 为空）+ 英文标签，**把用户明确选过的类别扔了去猜**，导致图库分类器「完全不工作」。助手在 0.1.5 那轮自认：

> 「是我理解错了，你说得对」

正确含义是卡片上 `作者_类别_分辨率` 那行的第 2 段，即 `library_file.content_category_id`。
**教训**：用户用的词是**界面上看得见的词**，不是数据库字段名。遇到歧义先问，或先把「这个词在界面上指什么」查清。

### 5.3 「移除本地词典数量」删少了，隔一轮才补上

用户原话是「**各页面**移除本地旧的词典数量等」。助手问了一次，用户答得很明确（seq 8323）：

> 「你理解错了了，**只有设置页的本地词典这一栏需要移除**，并替换中文模糊匹配词典相关的设置和介绍」

助手照此只改了 `SettingsPage` 一栏。但下一轮用户仍要补：

> 「并把搜索栏翻译服务中对于是否命中一开始我们采用本地方案的模块直接移除，**图库的本地词典数目也是**」

**教训**：用户说「只有 X」是在纠正范围过宽，同时他原本的要求「各页面」里还包含 X 之外的项。**纠正与原始要求要一起读**，不要因为被纠正就把原始清单里的其他项也丢掉。

### 5.4 被写进交接文档的错误结论：`curren_chan` 「能打中」

`handover-next.md` 第二节把 `curren_chan` 列进「能打中的输入（实测过）」，第五节又自己纠正：索引里的键是 `curren_chan_(umamusume)`，**不存在 `curren_chan` 这个键**，而片段档只从输入里切更短的片段，不会拿输入去前缀匹配更长的键。
**教训**：不要把「我试过一次好像行」写成「实测过的能打中的输入」。写实测结论时必须连**样本**一起写下来，否则无法复核。

### 5.5 被推翻的数值：短名档分数不是 0.80

交接文档原稿给出「`"prefix": 0.80`」，据此估的验收分数（0.80 量级）不对——实际分数还要乘分类权重与热度权重，「真机伶」落在 0.53–0.63。同一处还漏了一层：**同一个短名撞到多个词条时靠热度排序**，基础角色因此排在服装变体前面。这两点都是落地后才在文档第五节补的纠正。

### 5.6 `sample` 字段根本不存在

助手写预览探针时用了 `post["sample"]`，于是结果退回 180px 缩略图，看起来像「预览没生效」。实际 Danbooru 的 850px 大图叫 `large_file_url`，**客户端本来就映射对了**。检测逻辑错在探针，不在产品。
**教训**：检查别人的代码前先确认自己探针用的字段是真的（对照客户端实现，而不是对照记忆）。

### 5.7 Danbooru `/tags/<名字>.json` 不存在 —— 一次差点造成大破坏的误报

`verify_tags.py` 第一次跑出来说 **263 个标签全部不存在**。助手没有信，因为「`1girl` 当然存在」。查下去发现 Danbooru **没有 `/tags/<名字>.json` 这个端点**（任何请求都 404），正确写法是 `/tags.json?search[name]=<名字>`。
**这条为什么最危险**：它**安静地给出一整套看似可信的结论**。如果当时信了，助手会按报告把词典里 263 个正确的标签全部剔除。已在 `docs/context-handover.md` 记为第五轮缺陷，并加了联网用例锁住这个端点用法。

### 5.8 自己写进文档、又被自己实测推翻的判断

助手原写「`rating:g,s` 与 `rating:general` + `rating:sensitive` 两种写法等效」。实测：后者返回 **0 条**（同前缀的两次限定在站内取**交集**而不是并集）。并且只请求 `rating:g` 会**静默丢掉整个 s 档**（200 条里一条 s 都没有）——不报错、不警告，只是结果变少，表现是「搜泳装怎么没什么结果」，极难定位。

### 5.9 基于错误诊断的「修复」

助手先改了相似档的权重归因，随后自己推翻：「我的『修复』基于错误诊断——两个案例都是 `zh` 档，差别是**热度**不是档权重」，回退那部分只保留截断修复。**能自我推翻是好的，但代价是一轮返工。**

### 5.10 两次「用户描述的因果关系不成立，但现象真实」

- 用户说「慢，检查是否只用了单线程」→ 实测**不是单线程**，而是每张图新建连接 + 一次失败永久拉黑，比单线程还慢。
- 用户说「右侧 ui 一直无法显示图片」→ 实测**不是图片加载失败**，是 `set_columns` 这个方法**从头到尾没有任何地方被调用过**，列数永远停在写死的 6。
- 同类第三例（0.1.4）：用户报「右侧还是空的」，助手上一轮已修「列数算得对」，但这轮发现**算得对不等于算得及时**（视口可用宽度变化不触发 `resizeEvent`）。

**教训**：用户给的是**假设**不是结论，先取证再改；而且同一个现象可能有两层原因，修了第一层不等于修完。

### 5.11 「只查不改」这一次做对了

用户明确说「**先别别改文件**」，助手全程只读、只做探针，并给出「有一件事要你确认」（闪的是空白方块还是带文字的框、鼠标当时是否停在图上）——这是本会话里最规范的一次诊断。中途把「伶」打成「令」（`curren_chan` 与「潮流公主」对不上）后**自查纠正**，没有带着错字往下推。

### 5.12 删除类操作的风险点

- `-Clean` 构建**差点删掉用户正在跑的便携副本**（用户把 0.1.1 解压到 `installer/dist/PIC-FINDER-0.1.1/` 并在里面运行），幸好因文件占用失败。助手随后把「永远不要加 `-Clean`」写进交接文档。
- 助手在 0.1.4 报告里说「`installer/dist/` 下现在只有 0.1.2、0.1.3 两份解压副本，**没有看到 0.1.1 那份**……不是我删的——你如果还在跑 0.1.1，留意一下」。这是一条**未定论**的事，容易在后续被误读成「助手删了用户的东西」。
- 助手在 `TEST\PIC FINDER` 里发现用户 0.1.0 的在用副本时明确「**我没动**」，这一点处理正确。

### 5.13 用户直接否掉的三次助手推荐

| 助手推荐 | 用户决定 | 出处 |
|---|---|---|
| R18 分**三档**（理由是 `sensitive` 在服装类参考里是正当需求） | 「不用，gs 统一作为全年龄对待，qe 统一作为 r18 对待，**直接一刀切**」 → 两档布尔 | seq 3134 |
| 全量检索「一直取到站点给不出更多为止 / 后台继续且可停」 | 「选项1，**但是**新增图片的检索分批次，**只有用户点击翻页的时候再继续增加**」 → 否掉后台自动拉 | seq 8323 |
| 「移除本地词典数量」删到什么程度（给了三个选项） | 「**你理解错了了**，只有设置页的本地词典这一栏需要移除」 | seq 8323 |

**模式**：用户在**产品取舍**上很有主见、会直接改助手的推荐；在**技术实现**上则完全放手。助手提问的方式（给选项 + 标推荐 + 说明代价）是有效的，但**选项要覆盖用户真正想要的第三种可能**（例如「翻页时才继续取」既不是「一直取」也不是「限多少」）。

### 5.14 一条自我约束做得好、值得沿用的习惯

助手多次**拒绝凭估计写指标**：体积与冷启动「不能替你下结论，也不该凭估计写进文档」，必须实测；接口行为一律先实测再写代码（`rating` 语法、`limit` 截断、分页上限、`is_pending` 比例、大都会端点退役）。它也**先看许可证再看数据**（因为文章的仓库是 GPL-3.0，改找 MIT 的那份）。这两条是项目里最有价值的工作习惯，建议保留。
