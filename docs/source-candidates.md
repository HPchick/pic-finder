## 分类与来源策略

四类参考图的需求各不相同，因此检索源也不同。

| 类别 | 需求特征 | 合适的来源类型 |
|---|---|---|
| 人体姿势 | 结构准确、姿态明确 | 真人照片、人体参考站、三维姿态库 |
| 服装 | 实物细节、材质 | 实物图、写真素材 |
| 道具 | 实物细节、结构 | 实物图、博物馆藏品 |
| 场景建筑 | 透视正确、实景 | 摄影素材、实景照片 |

这四类都偏好写实素材。二次元成品图是各类别内部的补充来源，适用于参考表现手法。

## 通用底座：Openverse

Openverse 由 WordPress 基金会维护，是一个开放授权媒体的聚合搜索引擎。它是本项目最重要的发现。

### 为什么它重要

它同时满足三个条件。

1. 提供官方接口，可程序化检索。
2. 内容为开放授权，版权风险最低。这直接缓解 OQ-06 的版权提示问题。
3. 聚合了 Flicka、维基共享资源、博物馆开放资源等上游，覆盖照片、插画与矢量图。

因此四类参考都可以从它起步，Danbooru 只负责动漫成品图这一细分方向。

### 已核实的事实

**接口与认证。** 官方文档位于 <https://api.openverse.org/v1/>。匿名请求即可使用，官方说明匿名请求对多数用户已经足够，官网自身的浏览器请求也使用匿名方式。注册应用可获得更高额度。

**令牌流程。** 注册接口为 `POST /v1/auth_tokens/register/`，返回 `client_id` 与 `client_secret`。换取令牌的接口为 `POST /v1/auth_tokens/token/`，采用客户端凭据模式，令牌有效期 `expires_in` 为 36000 秒。

**额度信息接口。** `GET /v1/rate_limit/` 返回 `requests_this_minute`、`requests_today` 与 `rate_limit_model`。额度分三档：standard、enhanced、exempt。超出额度返回 429 状态码。

**检索接口。** 图片检索为 `GET /v1/images/`。支持下列参数。

- `q` 全文检索，长度不超过 200 字符。
- `license` 与 `license_type`：可选 `by`、`by-nc`、`by-nd`、`by-sa`、`cc0`、`pdm` 等，类型可选 `commercial`、`modification` 等。
- `mature` 默认 false，控制是否包含敏感内容。另有 `unstable__include_sensitive_results` 参数。
- `creator`、`tags`、`title`、`source`、`excluded_source`、`extension`、`filter_dead`。
- `page` 与 `page_size`，默认每页 20 条。
- 排序参数 `unstable__sort_by`，可选 relevance 或 indexed_on。

**两条必须注意的限制。**

第一，服务条款**明确禁止爬取**，原文说明在任何情况下都不允许。这意味着只能作为检索接口正常使用，不能用于批量下载全站内容。

第二，**分页深度受限**。官方说明单个查询只可查看最相关或最新的若干千条记录，设计意图是取前 1 万条最相关结果，不是穷举检索。匿名用户的单页大小与可用于查询的总条数都受限制，注册用户同样受总条数限制，但可以请求更大的单页。

### 对设计的影响

**必须保存授权信息。** 下载时必须记录授权类型与署名要求。这是使用开放授权内容的前提，不能省略。

**不能当作无限图源。** 它的定位是精准检索，不是批量采集。因此它在产品中的角色是覆盖面补充，而不是主力图源。

**置信度**

高。接口、参数与限制均来自官方文档。

## 本地标注模型：WD14 Tagger

这一项解决 OQ-17。

### 模型本体

模型本体由 SmilingWolf 发布，权威地址为 <https://huggingface.co/SmilingWolf/wd-v1-4-moat-tagger-v2>。

需要区分模型本体与调用它的工具。模型本体是上面的 Hugging Face 仓库。ComfyUI-WD14-Tagger 是社区编写的调用工具，它引用同一批模型。开发时应以模型仓库为准。

### 已核实的事实

**许可。** apache-2.0，允许商业使用。

**架构。** MOAT，即 Mobile Convolution and Attention。

**能力。** 支持评级、角色与通用标签三类输出，共 9083 个标签。

**评估结果。** F1 为 0.6911。

**训练数据。** 在 Danbooru 数据集上训练，训练使用的 TPU 由 TRC 计划提供。

**需要的文件。** 两个文件缺一不可，`model.onnx` 为模型权重，`selected_tags.csv` 为标签表。

**输出格式。** 输入一张图片，输出逗号分隔的 Danbooru 标签，例如 `1girl, long hair, looking at viewer, outdoors, smile`。这正是本项目需要的格式，因为检索目标就是 Danbooru 的标签体系。

**运行方式。** 通过 `onnxruntime` 在 **CPU** 上运行，官方扩展说明其速度已经足够快，不需要显卡。这一点很关键，即使主用户的显卡被其他任务占用也不受影响。

### 获取渠道

**海外源。** Hugging Face 的 SmilingWolf 仓库。

**国内源。** ModelScope 上有可用的镜像，这一点对本项目很重要，因为它决定了主用户能否顺利下载。

- <https://modelscope.cn/models/fireicewolf/wd-v1-4-moat-tagger-v2>
- <https://modelscope.cn/models/deepghs/wd14_tagger_with_embeddings>，该镜像覆盖 10 个模型。

因此程序应支持从国内镜像下载模型，并把海外源作为备选。

### 版本对比

模型库页面为 <https://huggingface.co/SmilingWolf/models>。各版本按发布时间与规模对比如下。

| 版本 | 参数量 | 发布时间 | 说明 |
|---|---|---|---|
| `wd-eva02-large-tagger-v3` | 0.3B | 2024-07-28 | 精度最高，体积最大 |
| `wd-vit-large-tagger-v3` | 0.3B | 2024-07-26 | 同为 0.3B 级 |
| `wd-swinv2-tagger-v3` | 98M | 2024-03-16 | 下载量最高 |
| `wd-convnext-tagger-v3` | 98.7M | 2024-03-16 | — |
| `wd-vit-tagger-v3` | 94.6M | 2024-03-16 | 最轻的 v3 |
| `wd-v1-4-swinv2-tagger-v2` | 96.2M | 2024-05-15 | — |
| `wd-v1-4-moat-tagger-v2` | 未标注 | 2023-05-20 | v2 通用默认 |
| `wd-v1-4-convnextv2-tagger-v2` | 未标注 | 2023-03-23 | 社区长期首选 |
| `wd-v1-4-convnext-tagger-v2` | 未标注 | 2023-03-23 | — |
| `wd-v1-4-vit-tagger-v2` | 未标注 | 2023-03-23 | v2 最轻 |

**版本区别体现在三处。**

第一是骨干架构不同，包括 EVA02、ViT、SwinV2、ConvNeXt、MOAT 等。架构决定精度与速度的平衡方式。

第二是参数量不同，跨越 94.6M 到 0.3B，相差约三倍。参数量越大，通常精度越高，但推理越慢、体积越大。

第三是训练数据版本不同。v2 使用 Danbooru v1.4 数据，v3 使用更新的数据。**这一条比参数量更重要**：小参数的 v3 模型可能比大参数的 v2 模型更准，因为它见过的数据更新。

**v4 的进展。** 模型库中已出现 v4 相关的数据集，但由于模型本体尚未发布，当前仍以 v3 为最新可用版本。程序应把模型列表做成配置项，以便 v4 发布后无需改代码即可切换。

**体积预算。** 开发者实测反馈，最大版本所在的仓库由 3 个约 1.26 GB 的权重文件组成，合计约 3.78 GB。这与此前文档中"体积较小"的描述不符，此处更正。

程序实际只需要 `model.onnx` 与 `selected_tags.csv` 两项，合计约 1.26 GB。另外两种格式属于冗余，不必下载。

因此设计上要求如下。

1. 默认使用 100M 量级的轻量版本，首次使用即可完成。
2. 0.3B 版本作为可选，在界面中明确标注其体积，由用户决定是否下载。
3. 两个档位都能用，区别只在标注质量。轻量版本不构成功能缺失。
4. 标准版的下载必须支持断点续传与国内镜像，因为 1.26 GB 在普通网络下耗时较长。完整版已内置模型，不受此项影响。

### 文件构成（已实测）

开发者核对了模型仓库的文件列表，结果如下。

| 文件 | 大小 | 是否必需 |
|---|---|---|
| `model.onnx` | 1.26 GB | 必需，推理用 |
| `selected_tags.csv` | 308 KB | 必需，标签表 |
| `model.safetensors` | 1.26 GB | 不需要，训练格式 |
| `model.msgpack` | 1.26 GB | 不需要，另一种序列化格式 |
| `config.json` | 634 B | 可选，架构配置 |
| `sw_jax_cv_config.json` | 469 B | 不需要，JAX 用 |
| `.gitattributes`、`README.md` | 小 | 不需要，元数据 |

同一套权重在仓库中以三种格式各存一份，因此仓库总体积约为 3.78 GB。程序只需 ONNX 与标签表两项，合计约 1.26 GB。

**这条事实改变了体积预算的结论。** 原先担心最大版本需要 3.78 GB，实际只需 1.26 GB。因此内置模型变得可行，见 DD-19。

### 版本选择

**默认。** 选用 v3 系列中 100M 量级的版本，例如 `wd-swinv2-tagger-v3` 或 `wd-vit-tagger-v3`。理由是数据较新、体积可控、CPU 推理速度可接受。

**可选。** `wd-eva02-large-tagger-v3`，精度最高，体积约 1.26 GB。

**v2 系列。** 仅作为兼容备选，不推荐默认使用，因为其训练数据版本较旧。

**关键参数**（这些参数属于调用工具，不同工具名称可能不同）。置信度阈值默认 0.35，角色名阈值默认 0.85，后者更高是因为错误的角色名比缺失更糟。

### 对设计的影响

**分发策略（已由 DD-19 定案）。** 提供两个安装包。标准版不含模型，首次使用时从国内镜像下载并缓存。完整版内置 `model.onnx` 与 `selected_tags.csv`，装完即用。

下载须支持国内镜像，并在镜像失败时提示用户手动放置文件。

标注只用于打标签与图库筛选，不用于移动文件。

由于它在 CPU 上运行，可以在后台低优先级批量处理，不阻塞界面。

**置信度**

许可、架构、标签数、评估结果与获取渠道均为高置信度，来自模型仓库与镜像站。运行方式来自调用工具的官方文档。

**待实测**

各模型的实际文件体积、单张推理耗时、以及各版本在本项目场景下的标签质量。本次未能取得体积的精确数值，不得估算后写入文档。

### 一项需要记录的澄清

开发者在讨论中提到了 Jev 类模型，并将其与图像分类模型联系在一起。经核实，两者无关，此处记录以免后续重复混淆。

Jev 是 TypeSafe 提出的 System One Model，定位是判别式决策模型，用于在 Agent 架构中承担路由、schema 校验与置信度评估。它的输出是严格类型化的值，而非开放式文本。典型延迟为 70 至 500 毫秒，输入价格约为每百万令牌 0.042 美元。它的准确率低于前沿大语言模型，属于用少量准确率换取大幅成本与延迟优势。它也不适合本地部署。

出处：<https://www.datacamp.com/blog/system-one-models-jev> 与 <https://m.36kr.com/p/3988164509711361>。

对本项目的结论：图像标注应使用 WD14 Tagger 这类专用标注模型，与 Jev 无关。

### 候选三：免费摄影素材接口

**候选包括**

Unsplash、Pexels、Pixabay。

**已核实的事实**

Unsplash 的免费额度为每小时 50 次请求，称为 Demo 状态，适用于学习、小型个人项目与测试。生产状态需提交申请，通过后提升至每小时 5000 次。申请要求应用实现**热链接展示图片并跟踪下载事件**。出处：<https://help.unsplash.com/en/articles/3887917-when-should-i-apply-for-a-higher-rate-limit>。

**对设计的影响**

禁止把图片转存到本站再展示这一要求，与本地下载归档存在张力。

开发者已就额度问题作出决定，处理方式如下。

**第一，做好额度提醒。** 程序维护每个来源接口的当日与当小时消耗计数，在设置页与检索页显示剩余额度。额度低于阈值时给出提示，而不是等到返回 429 状态码才报错。

**第二，做好注册指导。** 在设置页提供申请生产额度的操作指引，说明申请需要填写的材料，包括应用标题、描述、截图，以及必须实现热链接展示与下载事件跟踪。

**第三，限制单次检索的请求数量。** 单次检索对该来源的请求数设上限，避免一次操作耗尽额度。该上限可在设置中调整，默认值取保守值。

除上述三项外，检索结果应写入缓存，同一关键词在一段时间内不重复请求。

**结论**

Unsplash 可以作为备选来源，但不作为主力。若采用，必须先实现额度计数与提醒，否则用户体验会很差。

Pexels 与 Pixabay 的条款尚未核实，初步信息显示条款更宽松。

**状态**

Unsplash 已核实，处理方式已确定。Pexels 与 Pixabay 待核实。

## 一项待决策的判断：摆姿势工具可能优于图片检索

人体姿势类存在一个可能性，需要开发者决策后再确定是否纳入范围。

**问题**

照片只能提供单一角度的姿势。画师真实的困难往往不是找不到姿势，而是找不到恰好符合设想的那个角度与身形。三维可调姿势工具可以旋转、调整体型、导出多角度参考，在这一点上优于任何照片检索。

**因此需要决策三件事**

1. 这类能力是否属于本软件的范围。
2. 若属于，是接入第三方工具，还是自行实现简单的三维预览。
3. 若不属于，是否在界面上提供跳转到这类工具的入口。

**建议**

第一期不做。先记录该判断，待主用户试用初版后根据反馈决定。

## 核实记录

核实时间：最后一次访谈当日晚间。

核实方式：网络搜索与网页阅读。搜索与网页阅读由云端检索服务执行，不受本机网络限制。

**本机无法执行网络请求。** 经隔离测试确认，命令执行环境没有网络出口，全部出网请求返回失败，包括国内无需代理的站点。因此下列事项在本机无法验证。

- 各站接口的连通性与实际返回。
- 模型文件的实际体积。
- 速率限制的真实表现。

**故障定位过程。** 起初怀疑域名解析被代理软件接管，因为 `huggingface.co` 与 `github.com` 被解析为 `127.0.0.1`。随后确认本机代理为 PAC 模式，配置文件地址为 `http://127.0.0.1:12462/commands/pac`，实际监听端口为 7897，且未设置任何代理环境变量。浏览器读取 PAC 规则因此可以正常访问，命令行工具则不能。

但隔离测试表明这不是根本原因。命令执行环境对任意目标均无网络出口，因此无论是否配置代理都无法访问。凡需实测的部分，应改由开发者在自己的环境执行，见本文待核实清单。

**未能直连的站点**：本机将 `huggingface.co` 与 `github.com` 解析为 `127.0.0.1`，`danbooru.donmai.us` 解析异常。模型仓库的页面内容通过云端检索获取，未经开发者本机直接阅读。模型体积等数据因此未能取得，不得估算后写入文档。

## 结论

四类检索源的构成尚未定案，这是当前项目的阻塞项之一，对应 OQ-18。

已形成的方向性判断有三条。

第二，二次元图库只承担动漫成品图这一细分方向，不再作为四类参考的主力来源。

第三，本地图像标注采用 WD14 Tagger 系列模型，在 CPU 上运行，输出直接对齐 Danbooru 标签体系。分发策略由 DD-19 决定，标准版按需下载，完整版内置模型。
