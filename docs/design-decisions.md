# 设计决策记录

本文记录 PIC FINDER 的设计决策，编号为 DD-01 至 DD-25。每条包含结论、理由、影响与状态四项。

状态的含义如下：已确认表示用户明确认可，暂定表示已有倾向但待确认，待定表示尚未决定。

后续若推翻某条决策，不要删除它，改为标注已废弃，并写明被哪一条取代以及原因。

## DD-01 目标用户是画师

**结论**

主用户是一位画师朋友，开发者本人是次用户。所有需求默认按主用户非技术人员这一前提设计。

**理由**

用户明确表示，这个软件是为画师朋友检索参考图而做。

**影响**

界面易用性的优先级高于功能丰富度。任何需要读日志或改配置文件才能使用的功能，对主用户等于不存在。

本项目最大的风险是开发者凭想象替用户定义需求。因此尽早让主用户试用，是硬性里程碑。

**状态**

已确认。

## DD-02 采用双模式

**结论**

软件有两个入口。第一期只实现文字搜图，第二期实现以图找源，两者共用同一套图片元数据与本地图库。

**理由**

用户列出的目标站点中，ascii2d、IQDB、Google 识图、Bing 识图都属于以图搜图引擎，而 Danbooru 属于标签检索引擎。这实际上是两个产品。合成单一入口会让两边都做不好，拆成两个模式并共享图库则能互相增益。

**影响**

数据模型从第一天起就必须包含来源站、原帖链接、画师、站内标签、文件哈希等字段。

界面顶层需要容纳两个模式，同时不增加层级。

第二期的具体服务尚未调研，见 OQ-05。

**状态**

已确认。

## DD-03 站点优先级

**结论**

第一期自动检索以 Danbooru 为核心，Safebooru、yande.re、Konachan 为可配置附加项。

Pixiv 与 ArtStation 第一期不做自动抓取，改为填好标签后一键打开官方检索页。

Google 与 Bing 的图片检索接口不作为检索源，只在第二期作为以图找源候选。

**理由**

依据见《技术可行性调研》，核心事实有三项。

1. ArtStation 服务条款第 5 条禁止任何非网页界面的访问，并禁止把服务提供给第三方。把软件分发给朋友这一行为本身即违反条款。
2. Pixiv 官方从未提供接口。非日本 IP 会遇到 Cloudflare 验证，按人气排序属于会员功能。
3. Danbooru 系网站的自动化访问受官方支持，只需使用可识别的用户代理标识并遵守速率限制。这是唯一合规且稳定的路径。

**影响**

Danbooru 系图库覆盖的是四类参考中的动漫成品图部分。人体姿势、服装与道具、场景建筑三类还需要真人素材与实物素材来源，见 DD-18 与 OQ-18。

产品的竞争力从网站覆盖数量转移到翻译准确度，与用户选定的核心卖点一致。

需要额外实现跳转到官网检索的功能。这项功能只是拼接网址，成本极低。

未来若要解禁 Pixiv，应做成可插拔模块，且默认关闭。

**状态**

已确认。检索源的构成已被 DD-18 修订为按类别分别确定。

## DD-04 翻译层采用混合方案

**结论**

翻译层有两个可替换实现：本地词典始终可用，网络接口由用户自行配置。两者输出统一的格式，可以叠加。

未配置接口密钥时，软件保持完整可用，只是覆盖面下降。

**理由**

用户明确要求只走接口调用，不做本地推理。本地大语言模型推理需要数 GB 体积与大量算力，而翻译任务只用到语义能力的一小部分，成本与复杂度都不划算，因此第一期不做。用户同时选择了混合方案。

用户的网络环境无法保证。软件不应因一次接口失败而不可用。

**影响**

需要一个清晰的翻译层接口，输入中文，输出标签数组，便于替换与测试。

本地词典是可长期积累的核心资产。它应设计成可增量更新、可由用户覆盖的文件格式。

接口提示词本身也是资产，须允许用户修改，因为不同模型的效果差别很大。

**状态**

已确认。

## DD-05 接口接入策略

**结论**

支持多家服务商，统一使用 OpenAI 兼容的对话补全接口。

接口密钥由用户在设置页自行填写，软件不内置、不中转。

密钥保存在本地配置文件中，导出配置时默认排除。

**理由**

用户选择了程序内提供设置页、由用户填写自己密钥的方案，并要求多家可选、未填也能用。

由开发者自建中转服务会增加长期运维成本与密钥泄露面。

**影响**

设置页需要测试连接按钮，否则用户填错无从判断。

需要处理各家接口地址与模型名的差异，做成预设与自定义两栏。

成本由用户承担，因此界面应显示本次翻译消耗的大致令牌数，以避免用户担心被扣费。

**状态**

已确认。

## DD-06 技术栈

**结论**

开发者已确认如下方案。

| 层次 | 选择 |
|---|---|
| 语言 | Python 3.11 及以上 |
| 界面 | PySide6 与 Qt Widgets，原生桌面窗口，不用 Web 界面 |
| 数据库 | SQLite，单文件，与绿色软件定位契合 |
| 打包 | PyInstaller 目录模式 |
| 网络与解析 | `httpx` 与 `selectolax` 或 `BeautifulSoup`，待实测后定 |

**界面层变更说明。** 本决策原先推荐本地 Web 界面，即 FastAPI 加 HTML 与 CSS。开发者随后提出新要求：软件必须集成原生界面，用户点开即用，不使用浏览器式界面。因此界面层改为 PySide6。

**理由**

1. 开发者已掌握 Python，只需新增 Qt 的使用知识。用 Qt Designer 可视化摆放控件，比手写 CSS 布局更直观。
2. 界面层是原生控件，没有浏览器内核，也不需要维护本地 HTTP 服务的端口、进程与退出时序。少一层服务就少一类故障。
3. 网络请求、网页解析、SQLite 与图片处理的生态都在 Python 一侧，而这个项目的难点正是网络与解析。
4. SQLite 为单文件数据库，符合数据跟随文件夹迁移的绿色定位。
5. 开发者明确要求点开即用的集成界面。Web 界面方案虽然调试更便利，但不符合这条要求，故排除。

**备选方案与不推荐的理由**

Electron 与 Tauri 都用 Web 界面，前者要维护一个 Node 项目，后者要求学习 Rust，且都不满足集成原生界面的要求。

PyQt6 的界面能力与 PySide6 相同，但采用 GPL 授权。若软件将来分发给他人，授权会变复杂。PySide6 采用 LGPL，没有这个问题。

Tkinter 与 CustomTkinter 的体积与启动最优，但界面观感上限较低，图墙与滚动列表的表现明显不如 Qt。

Flet、Dear PyGui、Kivy 与 Flutter Desktop 的观感或启动与画师工具的定位不匹配，或者要求学习新语言。

纯 C 语言需要手写网络栈、字符串处理、JSON 解析与图片处理，会把大部分时间花在语言本身。Qt Widgets 也可用于 C++，但要求同时学习 C++ 与 Qt。

**影响**

界面层不再需要本地 HTTP 服务。因此第一期的启动流程简化为直接打开窗口，不需要处理端口占用与单实例服务。

退出时序、单实例运行与数据目录初始化仍然需要实现。

第二期的局域网访问能力仍然保留。若 OQ-14 将来需要 iPad 用浏览器访问本地图库，只要让图库访问那一层额外开放一个只读的本地接口即可，本机界面不依赖它。

界面尺寸相关指标重新设定，见 N-07。

**状态**

已确认。界面层由开发者确认为 PySide6 与 Qt Widgets。打包后的体积与冷启动耗时待实测，见 DD-20。

## DD-07 安装形态

**结论**

提供安装向导，可修改安装路径，可创建桌面快捷方式与开始菜单项。

安装产物完全自包含在一个文件夹内，不写注册表，不写入系统目录。卸载即删除该文件夹。

用户数据默认与程序同目录，首次启动时允许用户改到别处。

必须提供配置导出与导入功能。

**理由**

用户要求纯粹的绿色软件，同时要求一键安装的可执行文件。自包含安装包可以统一这两个要求。

配置导出机制由用户提出。它解决了绿色软件的一个固有问题：程序数据放在安装目录内，升级时容易被覆盖。

**影响**

安装器与主程序都必须遵守升级协议，只替换程序文件，绝不触碰数据目录与图库目录。

若安装到系统盘的程序目录，会因写权限不足而无法把数据写在程序目录内。安装向导须检测并提示，建议默认安装到非系统盘或用户目录。

需要定义配置的结构版本号，以保证未来格式升级时可以迁移。

**状态**

已确认，已实现。实践中有两处与本文不完全一致，都需要开发者确认，见 OQ-21：卸载只删程序文件而保留 `data/` 与 `library/`；安装程序在 `HKCU` 下写一条卸载登记项。两处的理由记在 `installer/readme.md`。

## DD-08 归档维度

**结论**

第一期内置两个元数据驱动的归档维度：按来源站与按画师。

同时提供按日期与按尺寸档两个纯技术维度，这两类维度没有判断风险。

不做人工智慧视觉风格分类。

架构上预留用户自定义分类能力，包括手工按氛围归档。

归档只作用于新下载的图片，绝不移动或重命名用户已有的文件。

**理由**

用户选择了按来源网站分与按画师分。这两项都属于元数据，软件的判断完全可靠。

用户同时提出要保留接口接入能力、提供多种自动分类、并允许自定义文件夹。

风格分类必须由人工智慧查看图片后判断，成本、延迟与错误率都高。判错会把用户的图库搞乱。按设计原则，默认不做。

**影响**

归档引擎应设计成规则列表加求值器，而不是硬编码的条件分支，这样增加维度不需要修改核心。

目录名与文件名必须做 Windows 合法性净化与长度截断。

需要提供规则预览功能，让用户看到最终的目录结构。

**状态**

已确认。

## DD-09 本地图库能力

**结论**

软件不仅下载图片，还要管理图片。已下载的图片支持下列操作。

- 按标签、画师、来源站、评级、分辨率、下载时间筛选。
- 对画师名、标签与标题进行全文检索。
- 按多个维度排序。
- 查看统计：张数、总占用、按站与按画师分布、缓存占用、清理入口。

**理由**

用户明确要求本地图库可检索、可筛选、可排序，并要求提供软件数据统计表，以便直观查看与管理占用。

**影响**

图库索引数据库的表结构是本项目的真正核心，需要慎重设计。

需要处理用户手工删除或移动文件的情况。启动时或手动触发一次库与磁盘的对账。

统计页是数据可管理这一信任的基础，应在第一期完成，成本较低。

**状态**

已确认。

## DD-10 下载失败处理

**结论**

批量下载中单张失败不中断整批。

失败项进入待处理记录，界面标红汇总，可以一键重试或导出清单。

失败原因须分类记录，包括原图被删、需要登录、网络超时、磁盘空间不足、文件名非法。

**理由**

用户选择了把失败项单独取出、界面标红、可以重试的方案。

**影响**

下载器需要任务队列、每站独立的限速器，以及退避重试机制，不能使用简单的循环实现。

**状态**

已确认。

## DD-11 数据目录

**结论**

数据目录默认与程序同目录。

首次启动时强制引导用户确认或指定数据目录。

用户可以把它改到任何位置，包括系统盘与移动硬盘。

修改数据目录时提供迁移已有数据的选项。

**理由**

用户最终的表述是：不必刻意避开系统盘，默认路径可以放在系统盘，但在安装或初次使用时必须让用户能够指定数据文件夹。这实际上是默认简单、决定权交给用户。

**影响**

需要一个首次运行向导，步骤极少，只需选择数据目录与图库目录。

数据目录的路径必须存储在程序目录之外的稳定位置，否则修改数据目录后程序无法定位。这是本设计中唯一的例外，具体方案见 OQ-09。

**状态**

已确认。细节已由 DD-22 落实，原先「步骤极少，只需选择数据目录与图库目录」中的图库目录改为由数据目录推导，不再单独询问。

## DD-12 内容分级

**结论**

现阶段不做最终决策。用户明确表示先保留这个问题。

实现上，各站的分级过滤参数必须做成显式开关，不得硬编码。

默认值建议为安全档，即 Danbooru 的 `rating:general`，Gelbooru 的 `rating:general`。

若将来软件要分发给开发者以外的人，此项必须重新决策。

**理由**

这是产品与伦理决策，不是技术决策。在技术上它只是一个请求参数。

**影响**

请求层需要支持注入分级过滤参数。

界面需要一个分级开关，默认收紧，开启需要确认。

调研指出，各站分级由社区众包标注，必然存在误标。因此 `rating:general` 不等于严格安全。

Gelbooru 的 `rating:safe` 已被废弃，必须改用 `rating:general`。

**状态**

已由 DD-21 与 OQ-20 部分取代。原先的「现阶段不做最终决策」作废，保留的部分是实现约束与三项技术事实。分级范围现为两档一刀切，开关位置与默认值以 DD-21 为准。

## DD-13 排序策略

**结论**

支持按标签匹配度、人气、分辨率、时间四个维度排序。

默认按加权混合排序，界面提供单维度一键切换，不提供多滑块权重调节。

**理由**

用户四个维度全部选择。用户同时强调减少子菜单层级、保持界面干净清爽。

让用户调节权重等于把困难推给用户，而用户并不知道自己想要的权重。

**影响**

需要一个可解释的评分函数。让用户看到某张图排在前面是合理的，但不应成为负担。

**状态**

已确认。

## DD-16 明确不做的事

**结论**

第一期不做下列各项。

## DD-17 本地图像标注模型

**结论**

允许在本地运行专用的图像标注模型，用于给已下载的图片自动生成标签。

该能力默认关闭，由用户在设置中显式开启。

标注结果只用于本地图库的筛选与检索，不用于自动分类，也不触发任何文件移动。

**理由**

主用户已更换绘画电脑，实际配置为 32 GB 内存与 5060 显卡，可以承担中等规模模型的推理。此前"绘画电脑性能较弱"的判断基于过时信息，已作废。

专用的图像标注模型与本地大语言模型有本质区别。前者体积在 1 GB 量级，推理快，输出确定，适合批量处理图片。后者体积以 GB 计，推理慢，不适合这个场景。

具体采用 WD14 Tagger 系列模型，其许可为 apache-2.0，输出直接对齐 Danbooru 标签体系。选型依据见 [source-candidates.md](source-candidates.md)。

**体积数据（已实测）。** 模型仓库中同一套权重以三种格式各存一份，因此仓库总体积约为 3.78 GB。程序只需 `model.onnx` 与 `selected_tags.csv` 两项，合计约 1.26 GB。仓库文件清单见 [source-candidates.md](source-candidates.md)。

由于实际体积为 1.26 GB 而非 3.78 GB，内置模型变得可行，模型的分发策略改由 DD-19 决定。

标注不联网，因此不产生费用，也不涉及把用户的图片上传到第三方。

**影响**

模型文件会显著增加安装包体积，因此分发策略需要单独决策，见 DD-19。标准版不内置模型，改为首次使用时下载并缓存。完整版内置模型，装完即用。

标注能力与网络翻译接口职责分离：前者处理已下载图片的内容标注，后者处理检索时的中文语义翻译。

标注会出错，尤其是风格类标签。因此只用于打标签与筛选，不用于移动文件。这符合设计原则 P2 与 P3。

**状态**

已确认。模型选型见 OQ-17，分发策略见 DD-19。

## DD-18 参考图的四类一级划分

**结论**

## DD-19 模型分发与安装包策略

**结论**

提供两个安装包。

| 安装包 | 体积量级 | 内容 |
|---|---|---|
| 标准版 | 不含模型，实测后标注 | 不含模型，首次启动时引导下载或手动放置 |
| 完整版 | 含模型，实测后标注 | 内置 `model.onnx` 与 `selected_tags.csv`，装完即用 |

内置时只打包 ONNX 格式，不打包 `model.safetensors` 与 `model.msgpack`。

**理由**

第一条理由是隔离网络风险。主用户的运行环境可能无法访问境外站点，本项目的开发环境已确认存在网络出口受限的情况。模型内置后，主用户不需要下载模型，直接绕开国内镜像、断点续传与下载失败这一整类问题。

第二条理由是开箱即用。标注功能在安装后立即可用，不需要等待一次 1.26 GB 的下载。

第三条理由是符合绿色定位。模型随程序目录存放，整个文件夹拷走即为完整环境。

第四条理由是控制冗余。仓库中同一套权重存有 ONNX、safetensors 与 msgpack 三种格式。程序只需 ONNX，另外两种格式合计 2.52 GB 属于不必要的体积。

**影响**

安装包体积原先超过 N-07 的 150 MB 目标。该目标已由 DD-20 取消，改为实测记录制。

维护两个安装包会增加打包流程的工作量。若不便维护，可退化为单一完整版。

模型不随程序迭代而变化，因此两个安装包的设计可以降低日常升级的下载量。日常升级只需重下标准版的程序部分。

**状态**

已确认。体积目标见 DD-20。

## DD-21 成人内容开关

**结论**

软件提供一个成人内容开关，位置显眼，默认关闭。

三条要求。

1. **显眼**。开关放在检索页的常驻可见区域，不藏在设置页，也不藏进下拉菜单。用户一眼能看到它当前是关的。
2. **默认关闭**。首次运行、新建数据目录、重置配置，三种情况下都是关闭。开启状态需要用户显式操作才改变。
3. **开启需要确认**。从关闭切到开启时弹一次确认，说明开启的后果。从开启切回关闭不弹确认。

关闭时的检索行为按下面的两档划分，并叠加本地黑名单标签。

**分级按两档一刀切。** 来源站的四个分级取值合并为两档。

| 档位 | 包含的来源站分级 | 开关状态 |
|---|---|---|
| 全年龄 | `general`、`sensitive` | 关闭（默认） |
| R18 | `questionable`、`explicit` | 开启 |

**因此关闭时请求的是两个分级值而不是一个。** Danbooru 系的请求语法里，同前缀的分级可以写成一个简写形式 `rating:g,s`，也可以写成两项 `rating:general` 加 `rating:sensitive`。两种写法等效，但**不得只请求 `general`**，否则会把 `sensitive` 一并排除，导致泳装与贴身衣物类参考也搜不到。

开关的状态记入 `config.json`，随配置导出。导出配置时不包含密钥这一规则不适用于本项，因为开关状态本身不是隐私数据。

**理由**

开发者的决定。原先由 DD-12 推迟，现在明确要求提供。

一刀切的理由是四档划分对使用者没有意义。主用户不会去分辨「轻度暗示」与「明显暗示」的区别，让她理解 `questionable` 与 `explicit` 的界线，等于把来源站的社区标注习惯转嫁给她。两档是她能自己判断的：全年龄，或者包含成人内容。

把 `sensitive` 归入全年龄是这一刀的关键取舍。`sensitive` 档包含泳装、贴身衣物、露肩、裸腿一类内容，这些在服装类参考里是**正当且必要的需求**。主用户搜「泳装」是为了画衣服，把它划入成人内容会直接伤到正常功能。代价是该档偶尔会有比预期更露的图。调研已记录这一事实：各站分级由社区众包标注，同一档内部的尺度并不完全一致。

默认关闭的理由有两条。主用户尚未就成人内容表态，这是 OQ-08 的内容。在得到她的答复之前，默认值必须取最保守的一档，否则等于替她做了决定。

显眼的理由与「默认关闭」并不矛盾。默认关闭保护的是初次使用者，显眼保护的是有意使用的人。把开关藏进设置页会让需要它的人反复翻菜单，而把它放在明面上对不需要它的人没有损失，因为默认是关的。

开启需要确认的理由是防止误触。这个开关影响的是图库里会出现什么内容，误触的后果比误触一个排序选项严重。

**影响**

检索页的布局需要为它留一个固定位置。这一项会影响 DD-14 的界面结构，具体位置见《简介》的检索页布局。

请求层需要接收一个布尔参数，据此决定注入哪些分级值。**这个布尔参数与分级值的映射必须集中在一处定义**，不得散落在各站客户端里。理由是各站的语法不同，而档位语义必须一致，分散定义迟早会出现某站漏掉 `sensitive` 的情况。

图库页与归档规则暂不受它影响。它只控制检索请求带哪些分级，不负责过滤已下载的内容。已下载内容的分级筛选是图库页的筛选功能，与本开关是两件事。

**状态**

已确认。位置、默认值与两档划分均已定。

## DD-22 首次运行向导

**结论**

首次运行弹一个窗口，只问一件事：数据放在哪里。

窗口内容的排版固定如下。

| 行 | 内容 |
|---|---|
| 第一行 | 程序目录，灰色只读，可选中复制 |
| 第二行 | 数据目录，可编辑的输入框，**右侧紧邻一个「选择文件夹…」按钮** |
| 第三行 | 图库目录，随上一行的输入实时更新，只读 |
| 提示行 | 该目录是否可写、是否已有图库、是否因为程序目录不可写而改放指针文件 |
| 按钮 | 「使用此目录」与「使用默认目录」 |

四条实现约束。

1. **向导必须先于建库。** 顺序是解析路径、向导、装日志、读配置、建库、开窗口。
2. **按确认时校验可写。** 不可写就留在窗口里，不允许带着一个写不进去的路径往下走。
3. **「使用默认目录」同样写指针文件。** 向导一辈子只出现一次。
4. **命令行与自动检查不弹向导。** 给了 `--data-root` 时以参数为准；`--smoke` 与 `--probe-search` 是无人值守的检查，模态窗口会把它们挂住。

指针文件的回退位置也在此确定：程序目录可写时用程序目录旁的 `portable.json`，不可写时改用用户本地应用数据目录下的同名文件。两个位置的读写判定必须一致，否则会出现写得进去却读不出来。

**理由**

向导必须先于建库这一条是实测踩出来的，不是推演出来的。原先的写法是先 bootstrap 再弹窗，于是窗口里写着默认目录，用户改到别处之后，默认位置已经生成了一份空的数据库与词典，而本次运行的日志里那句「数据目录」写的是旧值。两份数据、一份日志，用户与开发者都无从判断哪份是真的。

按钮放在路径右侧，是开发者的直接要求，理由也清楚：用户看到路径之后的第一个念头就是「换个地方」，按钮放在窗口底部或另一个标签页里，会让人先找一圈。

校验放在确认时而不是输入时，是因为校验要真建目录。输入时校验会在用户敲到一半的路径上留下空目录，所以输入时只做无副作用的探查，见 `paths.can_write_under`。

「使用默认目录」也写指针文件，是为了让向导只出现一次。否则每次启动都问一遍，而用户的回答从来都是默认值。

指针文件加用户目录回退，覆盖安装到 `Program Files` 的情形。若不加回退，程序目录不可写时指针无处可写，用户改过的数据目录下次启动就丢了，而那恰恰是最需要改目录的一类安装方式。

**影响**

`paths` 层新增两个函数。`for_root` 按给定根目录推导全部路径，不读指针也不碰磁盘；`can_write_under` 探查可写性但不创建目录。两者都是为向导的实时预览服务的。

界面层新增 `ui/first_run.py`，原 `main_window.py` 里那个只做告知的 `confirm_first_run` 删除。

启动入口拆成两条路径。`run_headless` 供 `--check` 使用，不弹向导；`run_desktop` 内含向导。两者各自负责关闭数据库连接与收尾日志，不再共用一个 `finally`。

**状态**

已确认。由开发者在试用第一版之后提出，界面布局与时机均已落实。

## DD-23 下载与归档的落地规则

**结论**

DD-08 定了归档维度，DD-10 定了失败处理，但都没说文件叫什么、目录怎么拼、重试几次。这一条把它们定下来。

**一、文件名形如 `画师_站点_作品编号.扩展名`。**

画师名未知时省略该段，例如 `danbooru_12316965.png`。每一段单独净化与截断，画师段上限 60 字符。整名超过 150 字符时丢掉画师段，作品编号永远保留。理由是编号保证唯一，画师名只是给人看的。

**二、归档目录按固定顺序拼接：来源站、类别、画师、日期、尺寸档。**

只拼启用的维度，未启用的不留空目录。前三项是元数据，从粗到细；后两项是纯技术维度，放末尾。目录名用站点的 `slug` 而不是显示名，理由是显示名可能改，改了会把已有目录劈成两半。

| 维度 | 目录名 | 说明 |
|---|---|---|
| 来源站 | `danbooru` | 取自 `source_site.slug` |
| 类别 | `姿势` | 取自 `content_category.name_zh` |
| 画师 | `some_artist` | 未知时用「未标注画师」 |
| 日期 | `2026-09` | 只到月，到日层级太深 |
| 尺寸档 | `大图` | 按像素数分档，见下 |

尺寸档的三个阈值取两个常见分辨率，因为画师熟悉这两个参照点。

| 档位 | 像素数下限 | 参照 |
|---|---|---|
| 大图 | 8 294 400 | 3840×2160 |
| 中图 | 2 073 600 | 1920×1080 |
| 小图 | 其余 | 含尺寸缺失以外的全部情况 |

**三、落盘用先写临时文件再原子改名。**

临时文件是同目录下的 `.<作品键>.part`，写完校验通过后 `os.replace` 改名。理由是断电或崩溃不会留下半张图，也不会让半张图被当成完整图收进图库。

**四、落盘之前必须查文件头。**

图片被删或需要登录时，站点可能返回一个状态码 200 的 HTML 错误页。只看状态码会得到一堆打不开的 jpg。实测中这条拦下过一次真实的返回。查不出图片格式的一律判为失败，并删掉临时文件。

**五、去重有两个时点，都在下载引擎里。**

| 时点 | 判据 | 结局 |
|---|---|---|
| 入队时 | `library_file.post_key` 已存在 | 已在库，不下载 |
| 入队时 | 站内给的 md5 已存在 | 跳过，不下载 |
| 落盘前 | 本地算出的 md5 已存在 | 跳过，删掉临时文件 |
| 落盘后 | 写库撞上唯一索引 | 跳过，删掉落盘的文件 |

后两个时点不可省。站点不总是给出 md5，而同一张图可能被作者发在两个站，字节日级相同。少了落盘后这一步，文件已经写进图库目录而记录写不进去，图库里就多出一个不被索引的孤儿文件。

**六、重试最多三次，只重试可重试的错误。**

| 分类 | 触发 | 重试 |
|---|---|---|
| `deleted` | 404、410 | 否 |
| `auth_required` | 401、403 | 否 |
| `timeout` | 超时、429、5xx | 是 |
| `no_space` | 磁盘满 | 否 |
| `bad_filename` | 路径非法 | 否 |
| `unknown` | 其余 | 是 |

退避取固定的一秒与两秒。不做抖动，因为每站已有闸门把请求压在每秒一次以内。

**七、并发是本地的三个线程，每站同时只允许一个请求。**

不开放给用户，见 OQ-10。三个线程是本地带宽与站点限速之间的折中，站点限速才是真正的瓶颈。

**理由**

文件名与目录规则必须写死并且只写一处。这一类规则一旦分散，表现是同一个画师的文件散在两个目录里，而且不会有任何报错。

先临时文件再改名的理由是所有下载器都要面对同一个问题：写到一半中断怎么办。原子改名是唯一能保证「目录里出现的文件都是完整的」的做法。

查文件头的理由来自实测。站点的错误页与图片共用状态码 200，只信状态码的下载器会把错误页存成图片，而且它不会报错，直到用户点开才发现。

去重要两个时点的理由来自测试。写用例时用两件不同作品但字节相同的图去测，第二次下载直接撞上 `file_hash` 的唯一索引，报 `IntegrityError`，而那时文件已经落盘了。也就是说这个漏洞在正常使用中会出现，只是在写测试之前没人碰到。

**影响**

新增 `src/picfinder/download/`，分命名、类型、引擎三个模块，都不依赖 PySide6，因此可以在无界面环境里用替身接口完整测试。

界面层新增下载按钮、进度条、失败原因汇总与一键重试。图墙卡片在下载完成后禁用勾选框并加「已下载」角标。

`download_task` 表按原设计使用，状态与 `error_kind` 的取值全部落在既有的 CHECK 约束内，不需要改表。

**状态**

已确认。命名与目录规则、四个去重时点、重试分类均已落实并通过测试。

下载进度与单张结果最初从引擎内部的下载线程发出，界面上的角标一个都不变，而图片全部下载成功、数据库全部写对。

原因是信号走了 `.connect(self.one_done.emit)` 这种写法。把信号当普通 Python 方法连接之后，从第三个线程发出的信号会被投递到工作线程自己的事件队列，而不是主线程的；等它转发到主线程时工作线程已经准备退出，事件被丢掉。

**信号到信号必须写成 `a.signal.connect(b.signal)`，不要写成 `connect(b.signal.emit)`。** 二者只在跨线程且发送方不是那个 QObject 所属线程时才有区别，因此这类错误只在真机上出现，单元测试抓不到。

## DD-24 中文翻译词典改用社区词表加模糊匹配

**结论**

手工整理的两百多条词典保留，但它不再是翻译的主力。新增一层社区维护的中文标签表，覆盖约十万个 Danbooru 标签，并在这两层之上做四档匹配。

**数据来源**

| 项 | 内容 |
|---|---|
| 仓库 | `github.com/amenorira/danbooru-tags-data-zh` |
| 许可证 | MIT，可以随程序分发 |
| 收录范围 | 图片数大于 50 的标签，覆盖至 2026-08 |
| 规模 | 99 951 个标签，98 226 个中文译名，155 549 个别名 |
| 字段 | `tag, category, aliases, zh, count, notes` |
| 体积 | 五个 CSV 合计约 9.7 MB |

**为什么不用作者推荐的那个项目的数据。** 用户提供的知乎文章介绍的 `DanbooruSearchOnline` 数据质量更高，但仓库是 GPL-3.0，把它的数据打进本程序会有许可证问题。MIT 这份的覆盖面已经够用。**先看许可证再看数据**，这一条写进流程。

**四档匹配**

| 档位 | 判据 | 例 |
|---|---|---|
| 精确 | 输入就是某个译名或别名 | 侧视 → `from_side`，夕阳 → `sunset`（别名） |
| 片段 | 输入里含一个更短的词条 | 雨天含雨 → `rain` |
| 相似 | 字符重合度过线 | 站姿与站立共享一字 → `standing` |
| 组合 | 切成两半各查一个标签再拼接 | 红色加眼睛拼出 `red_eyes` |

另有一档从标签注释里反查，只在前面几档都不理想时才用。「校园」查不到 school，但很多注释里写着「校园制服」，靠这一档捞回来。

**别名是这一层的关键。** 很多常用说法只出现在别名里，只看主译名会漏掉一大批：夕阳是 sunset 的别名，披风是 cape 的别名。

**排序**

分数 = 档位权重 × 分类权重 × 热度权重 × 相似度。热度用图片数取对数归一化，不能让常见的几个标签压过其余全部。分类权重把画师压到 0.7，因为画师名与人物名高度重名，实测中它反复挤掉真正想要的通用标签。

**理由**

用户实测反馈「翻译器几乎没用」。两百多条词典覆盖不了真实输入，输入「水手服」「回眸」这类常用词都可能查不到，而查不到不会报错，只是安静地给出空结果。

**不采用向量语义检索的理由。** 用户提供的文章用 bge-m3 做四视图语义匹配，效果更好，但代价是一个约 2 GB 的模型、一套 ONNX 运行时，以及为十万条数据建索引。本期先用确定性的词表加模糊匹配把覆盖率从几乎为零拉到可用，语义那一层留作下一步，接口已经预留：`GlobalTagIndex.candidates_for` 就是替换点。

**影响**

新增 `src/picfinder/translate/global_index.py`。词典文件多一层 `dictionary/zh/` 子目录，打包时必须带上，因此 `build.ps1` 与 `verify.ps1` 都加了对应检查：少了它程序照常启动，症状只是中文几乎查不到东西，不检查就发现不了。

索引在后台线程加载，约三秒，不拖慢开窗。第一次翻译会等它就绪。

**已知上限**

纯字面匹配接不住没有共同字符的说法。「似笑非笑」查不到 `light_smile` 或 `smirk`，「打伞」会被「打码」挤到前面。测试里有一条用例专门把这个上限钉住，将来加了语义检索它应当失败。

**状态**

已确认。四档匹配与真实数据上的质量基线均有测试，见 `tests/test_zh_dictionary.py`。

## DD-25 安装程序只做当前用户安装，永不提权

**结论**

安装程序固定按当前用户安装，向导里不提供「为所有用户安装」这个选项，也不请求管理员权限。

**理由**

三条，按重要性排。

一、**程序的数据要写在自己旁边。** DD-07 与 DD-11 决定了数据根目录默认就是程序目录。装到 `C:\Program Files` 之后这个目录不可写，程序只能退到用户目录，安装形态与设计不符。`paths.py` 里有这个兜底，但能不走就不走。

二、**多一个选项就多一条失败路径。** 模式选择页给出的「为所有用户安装」需要提权。开发者在这台机器上没有管理员权限，选到那条路径之后安装直接失败，一个文件都没写，界面上也没有能看懂的原因。当前用户安装这条路径从头到尾不需要提权，因此正确的做法是删掉那个选项，而不是写一份「请以管理员身份运行」的说明。

三、**权限越小越好。** 一个只把参考图存进用户自己目录的工具，没有理由写系统目录或 HKLM。

**做法**

保留 `PrivilegesRequired=lowest`，删掉 `PrivilegesRequiredOverridesAllowed=dialog`。`{autopf}` 于是稳定解析到 `%LOCALAPPDATA%\Programs`。目录页保留，用户仍可以改到别的盘。

**影响**

安装与卸载都不再弹 UAC。代价是装不了「所有用户共用一份」。按 DD-01 的目标用户（单人画师）判断，这个代价可以接受。

**同时留一个退路。** 打包脚本支持 `-Zip`，除安装程序外再产出一个便携压缩包。安装程序被杀毒软件或机器策略拦住时，解压即可运行。

**状态**

已确认。实录见 `docs/context-handover.md` 第 10.20 节。

## DD-26 结果分批取、界面分页看

**结论**

一次检索分两件事：向站点取几批，与界面上一次摆多少张。两者都可以由用户推进，互不绑定。

**理由**

一个热门标签在 Danbooru 上可能有几千张，例如 `oguri_cap_(umamusume)` 有 6893 张。一次取完要等几十批，用户面对的是一个不动的窗口；一次只取第一批又不够翻。

因此做法是：**先取第一批，用户翻到还没有内容的那一页时才去取下一批**。用户不看，程序就不请求，站点与本机都不被白耗。

界面一次摆多少张是另一个数量。它不决定向站点要多少条（那是站点硬上限与批量步长决定的），只决定一屏放几张、缩略图多大。因此可以放宽到 500 张一页而不增加任何网络请求。

**做法**

`SearchSession` 记住请求、目标站点、已取页数、已取回的结果与各站的结局。`fetch_next` 取下一批并合并。界面维护 `pool`、`page_index`、`per_page` 三样东西，翻到底时才调 `fetch_next`。

每页张数从 15 到 500 共六档，选择记进配置。缩略图尺寸跟着档位走，见 `ui/wall.py` 的 `thumb_size_for`：一页 15 张时边长 320 像素，一页 500 张时缩到 128 像素。用户选「15 张」是想看清细节，选「500 张」是想快速扫一遍，两种意图对应两种尺寸。

**状态**

已实现。实测见 `docs/context-handover.md` 的第十三轮与第十四轮。

## DD-27 并发数开放给用户

**结论**

缩略图与下载两项并发数放进设置页，改动立即生效，不要求重启。

**理由**

同一套默认值不可能同时适合两种情况：机械硬盘上的老机器，与千兆宽带下的新机器。原来把这两个数字写死在代码里，理由是 OQ-10 担心用户调到把站点惹火。这个担心对**来源站**成立，但对本机线程数不成立。

关键在于每条线仍然只有一个请求。站点限速由每站一道闸门单独负责（`download/manager.py` 的 `_SiteGate`），同一站点同时只允许一个请求，且遵守最小间隔。因此把线程数从 6 提到 16，只是让多站之间与同站排队之间的空隙被填满，某一站受到的请求密度没有任何变化。

**做法**

`config.Performance` 存两个数字，默认 12 与 6。范围分别是 1 到 32 与 1 到 16，设置页的调节框与配置的夹取共用同一对常量，避免界面能选到的值与配置接受的值慢慢不一致。

配置是用户可以手工编辑的文本文件，因此 `clamped()` 会把越界值夹回范围、把写成文本的坏值退回默认值，而不是抛异常。

缩略图的线程池是常驻的，改完当场换一个新的线程池；旧池不再收新任务，让它把手上那几张下完。不用 `cancel_futures`：被取消的任务不会发信号，那些地址会永远留在 `_inflight` 里，界面上的图就一直是「加载中」。下载的线程池是每批下载临时建的，下一批自然读新值。

**状态**

已确认。实测见 `docs/context-handover.md` 第十四轮。

## DD-28 设置页能改就改，地址改动立即生效

**结论**

设置页不再只读。凡是能当场生效的项，改完立即生效，不要求重启。地址用短框加「选择文件夹」按钮，不再用贯通整个页面的只读长条。

**理由**

上一版的设置页把所有路径排成五条贯通页面宽度的只读输入框。地址长了框里只能看到一截，想改又改不了，用户反馈「不符合直觉」。只读展示对开发者是省事，对用户是死路。

「立即生效」这一条是有代价的：改数据目录意味着重开数据库、重建中文词表、换掉缓存对象、把两个页面的图墙重新接一遍。但只写指针文件、要求用户重启，等于让用户点了「应用」却什么都没发生，那不叫设置项，叫占位符。

**做法**

数据根目录、图库目录、两项并发、归档规则、词表匹配范围、来源启用状态都做成可改。

数据根目录记在程序目录旁的 `portable.json`，不记进配置——配置本身存在数据目录里，把「数据目录在哪」也写进配置会形成循环。图库目录可以独立于数据根目录，因此记在 `config.Storage`，空字符串表示跟着根目录走。

切换数据目录的顺序是：先在新位置把库与词典建好，全部成功之后才换掉运行期的引用，中途任何一步失败都保持原样。日志文件不跟着走，本次运行剩下的日志与前半段留在同一个文件里，下次启动自然写到新目录。

**影响**

分级开关仍然只有检索页那一处。它是唯一一个放第二处就会造成两处状态不一致的项，见 DD-21。设置页只对它做只读说明。

**状态**

已确认。实测见 `docs/context-handover.md` 第十四轮。

## DD-29 图库按图片自带的文字信息分四类

**结论**

图库页按人体姿势、服装、道具、场景建筑四类筛选。分类依据是图片的标题与标签，规则全是关键词匹配，写在 `classify.py` 里，没有训练、没有模型、没有第二份规则。

**理由**

四类与 `content_category` 表的四行一致，也就是用户检索时选的那四类。图库按同一套类别归档，用户找参考图时不必在两套分类之间换算。

用户的要求是「分类依据直接读取图片标题」。实测之后这一条要补一句话：**安装版图库里那 50 张 Danbooru 图片，标题一栏全部为空，标签一栏 50 张全有**。只读标题的话，整个图库都会落到「未分类」，分类功能等于不存在。因此实际规则是标题优先、标签兜底，两边都在时得分累加。

**做法**

匹配带边界：关键词要落在标签的开头或紧跟下划线，结尾同理，并允许一个复数 s。这一条不能省，直接做子串匹配时 `rainbow` 会命中 `bow`、`sunglasses` 会命中 `glass`，道具类会被一堆无关的图灌满。

关键词分核心与辅助两级。核心词本身就能给图片定性，例如 `sitting`、`kimono`、`sword`；辅助词只是旁证，例如 `sky`、`looking_at_viewer`、`holding`。判定顺序是先只在有核心命中的类别之间比，核心命中一样多时比辅助命中，再一样多时按 pose、outfit、prop、scene 取前者。

过于通用的词不进表。`outdoors`、`solo`、`1girl` 这类标签几乎每张图都有，放进任何一类都会把整个图库染成那一类。

有一个词是故意不进的：弓。标签 `bow` 与发饰 `hair_bow` 共用这三个字母，边界规则挡不住它。实测 50 张里有 2 张因此被误判成道具类，去掉之后真正的弓靠 `arrow` 与 `quiver` 仍然认得出来。

标签的匹配结果按标签本身缓存。图库里的标签重复率极高，一万张图可能只有几千个不同的标签，缓存之后实际参与正则匹配的次数与图片张数几乎无关。

**影响**

一张图只归一类。实测那 50 张的结果是姿势 9、服装 41、道具 0、场景 0，偏斜来自测试数据本身：那批图的标签以 `bra`、`panties`、`bikini` 为主。分类只影响图库页的筛选，不改数据库，因此换一套词表不需要迁移任何数据。

**状态**

已确认。词表与实测见 `docs/context-handover.md` 第十四轮。

## DD-30 来源收敛成四个，四站各有各的取舍

**结论**

检索来源固定为 Danbooru、yande.re、Konachan、大都会艺术博物馆四站。老库里的其余来源在升级时自动删除或停用，见 `db/__init__.py` 的 `SEED_SITES_SQL` 与 `RETIRE_SITES_SQL`。

| Danbooru | 10 条 |

## DD-31 名字带括号后缀时，额外注册一个短名入口

**结论**

建中文标签索引时，除了主译名与别名，再为每个含空格的键注册一个「短名」入口，指向同一个标签。短名的分数权重 0.80，低于别名（0.90）、高于片段（0.62）。

**理由**

社区那十万条中文对照表用全角括号加限定词区分同名角色，例如 `curren_chan_(umamusume)` 的主译名是「真机伶（赛马娘）」。规范化把全角括号换成空格，真正的键是「真机伶 赛马娘」，**不存在单独的「真机伶」这个键**。用户只打「真机伶」时五档全打不中：精确档键不匹配；片段档只从输入里切更短的词，而「真机」「机伶」都不是词条；相似档的字符重合度被长度惩罚压到 0.257，远低于门槛 0.5；注释档的注释里没有这三个字；组合档要求输入至少 4 字，而「真机伶」只有 3 字。唯一过线的是 `fax_machine`（传真机），因为它与「真机伶」共享「真」「机」两字，得分 0.4414——用户看到的就是这么个莫名其妙的东西。

影响面实测：99951 条有中文名的词条里，22665 条（22.7%）的主译名带全角括号后缀，其中 20047 条（20%）的别名里没有短名兜底。约两万条词条光打中文名永远打不中。

**为什么不走另外两条路**

改词典数据要给两万条补短名，还要处理补出来的撞车，改动面太大且每次上游数据更新都要重做。改 `_dice` 的长度惩罚则不能动：那条惩罚本身有正当理由，去掉之后「A字站姿」会压过「站立」。

**做法**

`global_index.py` 的 `_load_files` 里，每条词条注册完主译名与别名之后，把它们规范化后的键逐个交给 `_short_name` 取第一个空格之前的部分，注册成 `kind="prefix"`。`_add_term` 自带按标签去重，同一个标签不会重复入桶。

三个细节是实测踩出来的，改这段之前必须知道：

1. **短名要无条件注册，不能只在键没被占用时补。** 同一个短名往往对应好几个词条，这正是要的结果。一开始按「键是否已被占用」判断，结果「真机伶」只命中了 `curren_chan_(umamusume)_(cosplay)`——那个词条正好把「真机伶」写成了别名，抢占了键位，而主词条的完整译名是「真机伶 赛马娘」，自己不会有「真机伶」这个键，于是被漏掉。现在每个词条都投自己的一票，撞车的几个按分数排序一起给用户。
2. **注册顺序：短名必须排在主译名与别名之后。** 反过来会先占住键，把真正的精确命中顶掉。踩过一次，当时「真机伶」的候选全部显示为「精确档 1.00」，其实走的是短名档。
3. **单字短名注册，单个西文字母或数字不注册。** 前者是「空（原神）」「萤（原神）」这类，拆出来就是单字，而它们正是用户会打的词；后者实测有三百多个，全是「i」「0」「1」这种消歧义符号或编号前缀，注册进去只白占键位。

**影响**

索引键数从 325975 涨到 339460（+4.1%），短名条目 28901 个，加载时间与内存没有可感的差别。这是纯索引层的改动，不碰数据文件，因此用户升级后不需要做任何事，也不必重新下载词典。

**已知的剩余不一致**

短名档的 0.80 低于别名档的 0.90，所以当甲词条把某个短名写成了正式别名、而乙词条只能靠短名档够到时，甲会赢。实测例子：`hina_(pajamas)_(blue_archive)` 把「空崎阳奈」写进了别名，于是它排在 `hina_(blue_archive)` 前面（0.6759 对 0.6630）。这是源数据自身不一致，不是短名档没生效——改之前基础角色根本不在候选里。这一档的定位是「把够得到的都摆出来」，最终顺序由用户在图库页面前自己定，见 DD-32。

## DD-32 翻译结果区把候选铺开，由用户决定留哪几个

**结论**

翻译结果区改成多行网格加滚动区，最多摆出 30 个候选。按钮带序号，会被检索式采用的前几个用绿底标出。「前几个」由 `config.search.max_tags_in_query` 决定，默认 2。

**理由**

用户的原话是「在翻译结果区域新增更多栏位空间，将命中的 tag 尽可能展示出来，由用户做决定留哪两个」。

原来的实现三处不到位：`run_translate` 用的是 `translate` 的默认 `max_tags=8`，词表往往能匹配出几十个候选，后面全被截掉，用户看不到也就无从挑选；标签区是单行水平布局，候选一多就挤成一条，根本看不过来；界面上没有任何地方说明哪几个会被送进检索式，用户不知道「删掉哪个有用」。

**为什么只取前 2 个**

匿名访问 Danbooru 一次最多两个标签，见 DD-16 与 `docs/feasibility.md`。所以程序只能送 2 个，那么「留哪两个」就必须由用户决定，而不是程序替他猜。

**做法**

标签区用 `QGridLayout`（每行 4 个）套一个 150 到 190 像素的 `QScrollArea`。最后一行不满时补空占位，否则按钮会被拉宽、每行宽度不一致。

两套底色各管一件事，不叠在同一个判断上：「会被检索式采用」那一组用绿底，是最要紧的信息；来源只区分手工（暖黄）与接口（浅蓝）两种非词典标签，避免和绿底抢眼。

按钮上带圈号，鼠标悬停时说明这个标签当前在不在检索式里、以及怎么让它进来。用户让某个标签进检索式的办法就是删掉排在它前面的那些——这是一个不需要额外控件的操作模型。

**一个顺手修掉的显示错误**

`result.uncovered` 的准确含义是「人工词典里没有、要交给中文标签表去查的片段」，不是「没认出来」。原来无条件显示，于是屏幕上会同时出现「未识别的内容：真机伶」和五个真机伶的候选——明明认出来了却说没认出来。改成只在整段输入一个标签都没翻出来时才提。

**影响**

`translate` 的 `max_tags` 默认值一并从 8 提到 30，与 `global_index.MAX_CANDIDATES_PER_SPAN` 同一个量级。候选多了以后按钮数量上升，但重建标签区用的是 `hide` 加 `deleteLater`，不是 `setParent(None)`，不会重现图墙那种闪窗，理由见 `docs/context-handover.md` 第十四轮。

**状态**

已确认。离屏实测见 `work/_ui015.txt`：输入「真机伶」摆出 5 个候选，「空崎阳奈」摆出 6 个，前两个绿底，删掉第一个之后第二个自动补进检索式。
