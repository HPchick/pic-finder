# 图库索引数据库设计

本文记录 PIC FINDER 的图库索引数据库设计。实现代码在 `work/db/schema.sql` 与 `work/db/build_db.py`，自检报告见 `work/db/build-report.txt`。

本文对应 DD-09「图库索引数据库的表结构是本项目的真正核心」这一判断。

## 设计范围

数据库负责四类数据。

| 数据 | 是否可重建 | 说明 |
|---|---|---|
| 图库记录与标签 | 否 | 用户已下载图片的索引，删掉就丢失管理能力 |
| 检索会话与结果 | 是 | 可重新检索得到，但保留可减少重复请求 |
| 下载任务队列 | 否 | 记录失败项与重试状态，见 DD-10 |
| 词典与用户覆盖 | 部分 | 内置词典可从文件重建，用户覆盖不可重建 |

配置、归档规则与接口密钥不放在数据库，放在 `config.json`。理由是它们需要用户可见、可手工编辑、可导出导入，对应 DD-07 的配置导出功能。数据库只存结构化程度高、需要按条件查询的数据。

## 表清单

共 16 张业务表与 2 张全文索引表，分四组。

### 图库组

| 表 | 职责 |
|---|---|
| `library_file` | 已下载图片的主记录，一行一张图 |
| `artist` | 画师，按来源站与画师名唯一 |
| `tag` | 标签字典，分类沿用来源站的标签类型 |
| `image_tag` | 图片与标签的关联，含权重 |
| `content_category` | 内置四类参考图 |
| `image_category` | 图片与类别的归属，一张图可属多类 |

### 检索组

| 表 | 职责 |
|---|---|
| `source_site` | 检索源及其代码行为差异 |
| `search_session` | 一次检索的条件，四类各自保存 |
| `search_result` | 检索结果与各维度评分 |
| `translation_cache` | 翻译接口调用的缓存 |

### 下载组

| 表 | 职责 |
|---|---|
| `download_task` | 下载任务与失败分类 |

### 词典组

| 表 | 职责 |
|---|---|
| `dictionary_entry` | 词典条目，来源为内置词典文件 |
| `dictionary_override` | 用户覆盖，与词典条目分开存放 |
| `tag_alias` | 标签的中文别名 |
| `runtime_state` | 运行期状态，例如磁盘对账时间 |
| `schema_meta` | 模式版本与创建时间 |

### 全文索引

`library_search` 与 `library_search_zh` 两表，见本文的全文检索一节。

## 七项设计决定

### 决定一：类别始终写入，但不强制作为目录

DD-18 要求归档目录预留类别维度，而《简介》的归档规则表里没有类别，这是接手时发现的设计缺口，已登记为 OQ-19。

本设计的处理是**把「记录归属」与「组织目录」两件事分开**。

`image_category` 表**始终写入**，由检索时的类别上下文决定。一张图可以同时属于多个类别，例如一张持剑站姿的图同时属于人体姿势与道具。

至于是否按类别建目录，交给归档规则。用户在设置页选择，默认建议不启用。

理由有三条。

1. 记录归属是**事实**，可以由检索上下文可靠确定。按类别分目录是**组织偏好**，不同用户差别很大。
2. 主用户是否按类别分文件夹尚未访谈。**不能替她决定**，但数据可以先存下来。等访谈有结论后，改一个配置即可，不需要数据迁移。
3. 一张图属于多个类别时，分目录必然要选一个主类别，这会引入一个不可靠的判断。存成多对多则没有这个问题。

因此 OQ-19 的建议答案调整为：数据库保留类别字段，默认归档路径不按类别分目录，待访谈确认后再决定是否启用。

### 决定二：标签同时以文本与关联表两种形式保存

`library_file.tag_string` 存原始标签串，`image_tag` 存规范化关联。这是有意的冗余。

写入时同时写两处，读取时分两种情况。

- **显示**用 `tag_string`，直接展示本站原始标签，不查表。
- **筛选与统计**用 `image_tag`，例如统计某标签的图片数、按标签组合筛选。

代价是两处可能不一致。控制手段是只允许通过仓储层写入，且写入在同一事务内完成。

### 决定三：四个唯一键分工明确

`library_file` 上有四个唯一约束，各自解决一类重复。

| 键 | 解决什么 |
|---|---|
| `post_key` | 同一站点的同一作品只入库一次，格式为 `站点:作品编号` |
| `file_hash` | 同一份文件不重复占用磁盘，覆盖跨站转载的同一张图 |
| `orig_url` | 作品换站后仍可识别，此为普通索引非唯一键 |
| `rel_path` | 同一物理文件只登记一次 |

`file_hash` 的唯一索引是**部分索引**，只约束非空值。原因是用户从本地添加图片时可能先入库、后计算哈希，允许暂时为空。

### 决定四：授权信息是一等字段

Openverse 等开放授权来源要求记录授权类型与署名。因此 `license`、`license_url`、`attribution` 三个字段建在图库主表上，而不是塞进一个通用 JSON 字段。

理由是这个数据必须能**按条件查询**。将来用户要筛出「可商用」或「需要署名」的图片时，字段化的列才查得动。

来源站本身也记录授权性质，`source_site.license_kind` 取值为 `open`、`site` 或 `unknown`。

### 决定五：下载任务的状态机

`download_task.status` 的取值与允许的迁移如下。

```
queued ──> running ──> done ──> archived ──> in_library
             │
             └──> failed ──> queued（重试）
             │
             └──> skipped（已存在，跳过）
```

三条约束来自 DD-10。

1. **单张失败不中断整批。** 状态按任务独立记录，不使用一个批次状态。
2. **失败原因分类。** `error_kind` 取值为 `deleted`、`auth_required`、`timeout`、`no_space`、`bad_filename`、`unknown`。分类是为界面能给出不同的处理建议。
3. **可重试。** `attempt_count` 与 `failed` 到 `queued` 的回边支持退避重试。唯一键 `(source_site_id, post_key)` 保证同一作品不会因为重试而堆出多条任务。

### 决定六：归档规则放在配置文件

归档规则不建表，存在 `config.json`。理由有三条。

1. 规则数量很少，不需要按条件查询。
2. 规则需要用户可见、可手工编辑、可导出，这些是配置文件的特征。
3. DD-14 要求设置项按内容分组，规则的界面形态是表单，不是列表。

数据库只在 `runtime_state` 里记录规则集的版本号，用于检测配置与已归档目录不一致的情况。

### 决定七：站点差异用列表达，不用代码分支

`source_site` 表把站点的代码行为差异显式列出来：接口类型、是否需要密钥、速率上限、是否要求自定义用户代理、授权性质。

这样新增一个站点只需插一行数据，不需要改检索逻辑。这是 DD-03 中「把每个搜索源做成可插拔模块」的落地方式。

种子数据已写入 7 个来源，全部默认 `enabled = 0`。理由是 OQ-07 尚未答复，默认关闭符合保守原则。

## 核心表的字段

| `post_key` | TEXT | 唯一键，格式 `站点:作品编号` |
| `post_url` | TEXT | 原帖链接，界面上始终显示，对应 OQ-06 |
| `artist_id` | INTEGER | 外键，画师 |

| `content_category_id` | INTEGER | 外键，主类别，供快速筛选 |
| `title` | TEXT | 作品标题 |
| `rating` | TEXT | `g`、`s`、`q`、`e` 或 `unknown` |

| `file_size` | INTEGER | 字节数 |
| `file_ext` | TEXT | 扩展名 |
| `file_hash` | TEXT | 文件哈希 |
| `file_hash_algo` | TEXT | `sha256` 或 `md5` |
| `orig_url` | TEXT | 原图地址 |
| `rel_path` | TEXT | 相对图库根目录的路径，唯一键 |
| `abs_path_hint` | TEXT | 上次见到的绝对路径，仅用于排错 |
| `tag_string` | TEXT | 原始标签串 |
| `tag_count` | INTEGER | 标签数，冗余用于排序 |
| `license`、`license_url`、`attribution` | TEXT | 授权信息 |
| `source_created_at` | TEXT | 站内发布时间 |
| `downloaded_at`、`archived_at` | TEXT | 下载与归档时间 |
| `created_at`、`updated_at` | TEXT | 记录时间 |
| `missing_at` | TEXT | 非空表示文件已从磁盘消失 |

`rel_path` 存**相对路径**而不是绝对路径，这样整个图库目录可以整体搬走，符合绿色软件定位。`abs_path_hint` 只用于排错提示，不参与定位，因为数据目录可以被用户在设置里改到别处。

`missing_at` 支持 DD-09 要求的库与磁盘对账。对账发现文件消失时置上时间戳，不删除记录，符合 N-09「任何自动操作不得删除用户已下载的图片」。

## 全文检索与中文的处理

图库需要按画师名、标题、标签做全文检索，对应 DD-09。设计上有两条实测结论，它们直接决定了实现方式。

### 实测结论一：trigram 分词器提供子串匹配

用 `trigram` 分词器建索引后，`MATCH '"边少女"'` 能命中「海边少女与鲸鱼」。这解决了中文无法按词切分的问题，不需要引入分词库。

### 实测结论二：查询串少于三个字符时一律返回零条

同一个索引下，查「肥鱼」命中不到「大肥鱼」，查「鲸」命中不到任何东西。原因是 trigram 只对三个字符及以上的查询做子串匹配，更短的串没有对应的词元。

这条边界的实际影响很大，因为中文画师名常常只有两三个字。

### 因此采用双索引加兜底

| 索引 | 分词器 | 用途 |
|---|---|---|
| `library_search` | `unicode61` | 拉丁标签与画师名的词匹配 |
| `library_search_zh` | `trigram` | 中文画师名与标题的子串匹配 |

查询层按下述规则选择路径。

1. 查询串长度大于等于 3，走 `library_search_zh` 的 `MATCH`，这是走索引的快路径。
2. 查询串长度为 1 或 2，走 `LIKE '%串%'` 的全表扫描。个人图库的量级在数千到数万张，这个扫描的代价可以接受。
3. 拉丁标签查询走 `library_search`。标签是空格分隔的记号，`unicode61` 正好合适。

两张索引表都由触发器与 `library_file` 同步。触发器是必需的：手工维护索引迟早会出现索引与内容不一致，而全文检索的不一致是**静默错误**，查不到数据却不报错，最难排查。

## 模式版本与迁移

`schema_meta` 表存 `schema_version` 与 `created_at`。当前版本为 1。

迁移约定有三条。

1. 每次改动表结构必须递增版本号，并在代码里登记一段迁移。
2. 迁移只在程序启动时执行一次，且必须在一个事务内完成。
3. 迁移前自动备份数据库文件，备份失败则中止迁移。不可再生数据不能冒迁移失败的风险。

`config.json` 也需要独立的结构版本号，两者分开演进。

## 实现约定

### 连接设置

每个连接打开后必须执行三条 PRAGMA。

| 设置 | 值 | 原因 |
|---|---|---|
| `journal_mode` | `WAL` | 允许下载线程写入的同时界面读取 |
| `foreign_keys` | `ON` | SQLite 默认关闭外键，必须显式打开 |
| `busy_timeout` | `5000` | 毫秒。避免并发写入时立刻报数据库被锁 |

`foreign_keys` 这一条特别容易漏。SQLite 默认不强制外键，漏掉之后所有 `REFERENCES` 都变成注释，数据损坏不会报错。

### 时间戳格式

全部存 UTC 的 ISO 8601 文本，形如 `2026-10-07T12:00:00Z`。

选择文本而不是 Unix 时间戳，理由是可读性与可排错性。ISO 8601 的字典序与时间序一致，因此排序与范围查询仍然走索引。界面显示时按本地时区转换。

### 并发

第一期采用单写线程加连接池的方案：所有写入排队到一个线程，读取可以并发。理由是 SQLite 的 WAL 模式允许一写多读，而下载任务天然是串行队列。

不使用多进程写同一个库。文件锁与 `busy_timeout` 能让它工作，但会让失败模式变复杂，不值得。

### 图片文件本身不入库

数据库只存索引，图片存在文件系统上，由 `rel_path` 指向。

不把图片存成 BLOB 的理由有三条：图库需要用户能用资源管理器直接看到和管理文件；大文件出入数据库会显著放大数据库体积与备份代价；DD-08 的归档要求落在真实目录上，数据库存 BLOB 无法满足。

## 自检

`work/db/build_db.py` 每次重建数据库时执行 19 项自检，覆盖四类约束。

| 类别 | 检查项 |
|---|---|
| 唯一键 | `post_key`、`file_hash`、`rel_path` 三者的重复写入必须被拒绝 |
| 外键 | 不存在的来源站必须被拒绝 |
| CHECK | 非法 `rating` 与非法下载状态必须被拒绝 |
| 生成列 | `pixel_count` 必须等于宽乘高 |
| 关系 | 一张图可同时归入多个类别；删除主记录时级联清理关联 |
| 全文检索 | 插入与更新触发器必须同步索引；中文 3 字命中与 2 字兜底两条边界 |

自检有两条实现上的注意事项，都是排查中实际踩到的。

1. **每个用例必须包在独立的保存点里。** 早期版本用整体回滚，结果第一条用例之后的失败把基准数据一起回滚了，后续用例全部报外键错误，看起来像表结构有问题。
2. **每个唯一键用例的其余字段必须互不冲突。** 早期版本测 `file_hash` 的那条新行用了重复的 `post_key`，于是先被另一个唯一键撞掉，测不到目标约束。

若自检出现失败项，报告会输出 `[失败]` 前缀并附 SQLite 的实际报错，不要忽略。
