# 下一轮访谈清单

本文是准备向主用户提问的问题清单，用于推进界面形态、内容分级与流转方式三类未决问题。

本次访谈的目标只有一个：把「开发者凭想象替用户定义需求」这一项目最大风险压下去。因此问题以还原现状为主，不以介绍功能为主。主用户是非技术人员，任何需要她理解实现细节的问题都应该重写。

## 使用方法

按三个优先级分批提问，一次访谈不必问完。

提问时遵守四条约定。

1. 先问现状，再问期望。现状是可核实的事实，期望容易受提问方式影响。
2. 不要提出方案让她选择，先让她自己描述。她描述完之后再拿方案对照。
3. 不要承诺功能。她的回答是需求输入，是否实现由开发者决定。
4. 原话逐字记录，不要转述成开发者的理解。记录进 `docs/interviews.md`，编号沿用 OQ。

## 第一批：最高价值

这一批解决四个问题，其中前两问价值最高。它们不依赖界面设计，也不需要她理解任何技术概念。

### 问 1：她现在的参考图放在哪里

这是本次访谈最重要的一问，用于推进 OQ-19。

- 她找到参考图之后，图存在哪里。电脑的哪个盘、哪个文件夹。
- 文件夹是软件默认的下载目录，还是她自己去整理过的。
- 这些图现在的文件名是什么样的，她能看懂吗。
- 如果按文件夹分类，分了几层，每一层的名字是什么。

**转述方式。** 可以请她直接截一张资源管理器的图。

**为什么要问。** 本软件约定不移动、不重命名用户已有的文件，只处理新下载的图。因此她的现有习惯决定了归档规则应该长什么样。若她本来就不分类，那么按类别分目录只会给她添麻烦；若她已经在按类别分，那么软件必须能对上她已有的名字。

### 问 2：她能描述一次完整的找参考过程吗

用于推进 OQ-02 与 OQ-16。

- 上一次找参考是什么时候，画的是什么东西。
- 她先打开什么，在哪里搜，搜的时候输入什么词。
- 找到图之后做了什么，是存下来还是照着画。
- 从中途卡住到找到参考，花了多久。

**为什么要问。** 这是唯一能验证「主动检索」这一结论是否成立的方式。它同时暴露真实痛点在哪一步，是搜不到、还是搜到了不好用、还是存下来找不到。

### 问 3：她对着屏幕会怎么用

用于推进 OQ-02。

- 她习惯打字描述，还是习惯点现成的词。
- 一次搜出来的图，她会挑几张，是一次挑几十张还是每次只挑三五张。
- 屏幕上同时显示多少张她看着舒服，是多一点还是少一点。
- 她用多大的屏幕看，是笔记本自带的屏还是外接显示器。她是否用触控板。

**为什么要问。** 这四条决定输入框是否需要常用词面板、图墙密度、下载队列的交互方式，以及控件的大小。

### 问 4：成人内容她怎么处理

用于推进 OQ-08。这是一个敏感问题，建议由开发者本人以自然的方式提起，不要由第三人转述。

- 她平时搜参考时，会不会因为图库混杂而受到干扰。
- 她希望默认搜出来的结果是干净的吗。
- 如果有一个开关，默认关着，需要她自己去打开，她能接受吗。

**为什么要问。** 技术实现上它只是一个参数，但默认值影响她对自己电脑里存了什么的感受。开发者的既有倾向是默认收紧，这一问用于验证而不是推翻。

## 第二批：重要

### 问 5：参考图怎么用到 iPad 上

用于推进 OQ-14。

- 她在电脑上存的参考图，最后怎么到 iPad 上。
- 她有没有用过云盘、相册同步或者隔空投送。
- 如果要在 iPad 上看电脑里的图库，她是愿意的，还是觉得多此一举。

**为什么要问。** 主用户的绘图主力设备是 iPad，如果流转这一步太麻烦，软件的价值会打折。这一问决定第二期是否需要局域网访问。

### 问 6：场景建筑与道具的使用频率

用于推进 OQ-18。

- 她画场景多吗，是画整张场景还是只画人物加简单背景。
- 除了人物持武器，还有什么情况会让她去找道具参考。

**为什么要问。** 人体姿势是已确认的主力需求，服装与道具需要分开也已成结论。场景建筑类由开发者提出，主用户只是未否认。这一问用来判断该不该为它单独投入检索源。

## 第三批：可以顺带问

- 她搜参考时最不顺的一步是什么，是想不到词、搜不到想要的角度，还是嫌麻烦。
- 她会不会把某张图反复当参考用，需不需要「收藏」这类入口。
- 她上网主要用电脑还是 iPad。
- 她愿意花多少时间等一次检索出结果。
- 有没有哪个网站是她特别信任或特别不喜欢的。

## 不能问的问题

下列问题对主用户没有意义，或者会引导出无效答案，避免提问。

- 不要问界面控件应该叫什么名字、放在哪个位置。
- 不要问她希望安装包多大、启动多快。
- 不要问她要不要命令行版本。
- 不要把 DD 编号、OQ 编号或任何文档术语说给她听。
- 不要问「要不要人工智慧自动分类」这类需要她判断风险的问题。

## 记录模板

每次访谈按下列结构追加到 `docs/interviews.md`，编号续写，例如第三次访谈。

| 项 | 内容 |
|---|---|
| 时间 | 访谈日期 |
| 方式 | 当面、语音或文字 |
| 问题编号 | 对应上一节的第几问 |
| 主用户原话 | 逐字，不改写 |
| 转述与解读 | 开发者的理解，与转述分开写 |
| 待澄清 | 未获答复或答复含糊的部分 |

**注意。** 主用户原话与开发者解读必须分开写。两者混在一段里，将来无法判断哪一句是她说的。

## 访谈之后

按下列顺序处理结论。

1. 把已经明确的问题从 `open-questions.md` 移到「已解决的问题」表。
2. 若结论推翻了某条 DD，不要删除它，改为标注已废弃并写明取代者。
3. 更新 `readme.md` 与 `context-handover.md` 中的编号区间与状态。
4. 把仍然含糊的部分留在清单里，标注为待澄清，不要凑一个答案填进去。
