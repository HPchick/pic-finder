## 1. 项目是什么

PIC FINDER 是一个面向画师的参考图检索与归档工具，运行于 Windows。

核心能力分两个模式。

1. **文字搜图**：用户输入中文描述，程序翻译成图库标签，跨站检索参考图，勾选下载并自动归档。这是第一期内容。
2. **以图找源**：用户丢入一张图，程序查询以图搜图服务，返回原帖与画师。这是第二期内容。

真正的技术含量在第一模式，即把中文意象翻译成图库标签。开发者的原话是核心卖点为"翻译得准"。

## 4. 主用户访谈结论（已核实）

完整原话见 `docs/interviews.md`。

**参考图的用途**：为了作画，不是灵感，也不是收集好看的图。她明确排除了后两者。

- 灵感不通过检索获得，来源是听歌与看文案。
- 收集好看的图用微博小号关注画师，依靠平台推荐流。

结论：本软件不承担发现好看的图这一职责。

**使用触发场景**：两种。需要一个特定姿势或构图时，以及画到卡住需要参考时。都属于主动检索。

**参考图分类**：她本人给出并认可四类，即人体姿势、服装、道具、场景建筑。其中人体姿势是主力需求，道具属于条件触发。

两条派生的设计结论。

1. **服装与道具必须分开**。她指出分开可以提高检索效率。
2. **动漫图不单列**。动漫成品图是四类各自的来源之一，不是独立类别。
3. **聚合发生在类别内部**，不是把四类结果混在同一屏。

**尚未确认的需求**：界面操作习惯、参考图流转到 iPad 的方式、成人内容策略、场景建筑类的使用频率。

## 5. 技术调研结论（已核实）

完整内容见 `docs/source-candidates.md` 与 `docs/feasibility.md`。

### 5.1 可用的检索源

**Openverse**，已核实，是最重要的发现。

- 由 WordPress 基金会维护，聚合开放授权媒体。
- 官方接口 `https://api.openverse.org/v1/`，**匿名即可访问**，注册后额度更高。
- 内容为开放授权，可用 `license` 与 `mature` 参数过滤。这大幅缓解版权问题。
- **两条限制**：服务条款明文禁止爬取；分页深度受限，官方设计意图是取前 1 万条最相关结果。
- 定位：版权干净的通用底座与覆盖面补充，不是无限图源。

**Danbooru 系**：接口官方支持，无需登录，速率限制为每秒 10 次、官方建议长会话压到每秒 1 次，必须用可识别的用户代理标识。

**大都会艺术博物馆**：提供开放获取接口，返回 JSON，含公共领域高分辨率图片。适合道具与服装类。

**Unsplash**：demo 额度为每小时 50 次，生产额度需申请且**要求热链接展示并跟踪下载事件**，与本地归档存在张力。开发者已决定：做好额度提醒与注册指导，并限制单次检索请求数。

**ModelScope**：国内镜像站，可下载 WD14 模型。这对主用户很重要。

### 5.2 明确不可用的检索源

**Pixiv 与 ArtStation** 的程序化访问明确违反其服务条款。ArtStation 条款第 5 条甚至禁止把服务提供给第三方，即分发给朋友本身就踩线。因此只做"填好标签后一键跳转官网"。

**人体姿态参考站**（Line of Action、SketchDaily 等）未发现公开接口，初步判断需重新设计方案。

### 5.3 本地标注模型

**WD14 Tagger**，仓库为 <https://huggingface.co/SmilingWolf/wd-v1-4-moat-tagger-v2>。

- 许可 apache-2.0，9083 个标签，在 Danbooru 数据上训练。
- **输出直接是 Danbooru 标签**，与检索标签体系对齐，省掉一层映射。
- 通过 `onnxruntime` 在 CPU 上运行，不需要显卡。
- 国内镜像：<https://modelscope.cn/models/fireicewolf/wd-v1-4-moat-tagger-v2>

版本差异有三处：骨干架构、参数量、**训练数据版本**。第三处最重要，v3 用 2024 年数据，v2 用 Danbooru v1.4 数据，因此小参数的 v3 可能比大参数的 v2 更准。

参数量对照：`wd-eva02-large-tagger-v3` 为 0.3B，`wd-vit-large-tagger-v3` 为 0.3B，`wd-swinv2-tagger-v3` 为 98M，`wd-convnext-tagger-v3` 为 98.7M，`wd-vit-tagger-v3` 为 94.6M，`wd-v1-4-swinv2-tagger-v2` 为 96.2M。

**文件构成（开发者实测）**：仓库中同一套权重存三种格式，总体积约 3.78 GB。程序只需要两项。

| 文件 | 大小 | 是否必需 |
|---|---|---|
| `model.onnx` | 1.26 GB | 必需 |
| `selected_tags.csv` | 308 KB | 必需 |
| `model.safetensors` | 1.26 GB | 不需要 |
| `model.msgpack` | 1.26 GB | 不需要 |

### 5.4 一项需要避免重复的混淆

开发者在讨论中提到"Jev 类模型"，并将其与图像分类模型联系起来。经核实两者无关。

Jev 是 TypeSafe 的 System One Model，定位是判别式决策模型，用于 Agent 架构中的路由与 schema 校验，输出严格类型化的值，延迟 70 至 500 毫秒，云端服务，不适合本地部署，与图像标注无关。

图像标注应使用 WD14 Tagger。此结论已写入 `docs/source-candidates.md`，不要重复混淆。

### 5.5 模型体积与分发（已实测与已定案）

开发者实测了模型仓库的文件构成，结论有两条。

第一，仓库中同一套权重存三种格式，总体积约 3.78 GB。程序只需要 `model.onnx` 与 `selected_tags.csv`，合计约 1.26 GB，另外两种格式属于冗余。

第二，分发策略由 DD-19 定案，提供两个安装包。标准版不含模型，首次使用时下载并缓存。完整版内置模型，装完即用。

先前文档中"模型不随安装包分发"的表述已作废，不要再据此设计。

## 10. 环境陷阱（重要，避免重复踩坑）

这些是本次会话实际遇到的问题，新窗口应按此处理。

### 10.1 网络出口：Python 可用，PowerShell 不可用

**这一节在第四轮被推翻并更正，早前的记录有误。**

早前的结论是「命令执行环境没有网络出口」。该结论来自 `curl` 与 `Invoke-WebRequest` 的失败，但失败原因是 TLS 与代理处理，不是没有出口。

第四轮实测确认：**Python 一侧可以正常访问外部接口**。已用 `httpx` 成功抓取 Danbooru 标签 2000 条，也解析了 `danbooru.donmai.us` 与 `api.openverse.org`。同一台机器上 PowerShell 的 `Invoke-WebRequest` 访问任意目标仍然失败，包括 `registry.npmmirror.com`。

因此处理方式如下。

| 目的 | 可行途径 |
|---|---|
| 实测外部接口 | 用 Python 写脚本，`httpx` 可用 |
| 抓取网页内容 | 用 Python，或用 `web_search` 与 `read_page` |
| PowerShell 直接联网 | 不可行，不要浪费时间 |

依赖安装也已完成。本机 Python 3.13.15 下已装 PySide6 6.11.2、PyInstaller 6.22.3、httpx 0.28.1。若需重装，用国内镜像：


### 10.1.1 不要用 PowerShell 管道捕获程序输出

命令执行环境拦截管道捕获，`python ... | Out-File` 或 `| Select-Object` 会报 `Access is denied`。

因此需要读取程序输出时，让程序自己写文件。`python -m picfinder --check --report 路径` 就是为此设计的。读取文件用 `Get-Content -Encoding UTF8`。

另外，终端显示的 Python 中文输出可能是乱码，那是控制台代码页的问题，写入文件的内容是正确的。判断程序行为以文件内容为准。

### 10.2 域名解析被代理接管

本机代理为 PAC 模式，配置文件地址 `http://127.0.0.1:12462/commands/pac`，实际监听端口 7897，未设置任何代理环境变量。

`huggingface.co` 与 `github.com` 被解析为 `127.0.0.1`，`danbooru.donmai.us` 解析异常。浏览器因读取 PAC 规则可正常访问，命令行工具不能。

开发者已确认这两个网站用浏览器可以正常打开。**不要因此判断是网站故障或额度问题。**

### 10.3 文件写入需要提权，且曾因文件被占用失败

工作区默认为只读。写入需要请求 `workspace-write` 权限，会向开发者弹出确认。

曾出现 `ReplaceFileW EIO (Win32 32)` 错误，原因是开发者打开了该文件，编辑器持有文件锁。解决方式是请开发者关闭文件。

**开发者曾拒绝一次提权请求，理由是工具试图绕过被拒的操作。** 遇到权限被拒时应停下并向开发者说明，不要用其他方式绕过。

### 10.4 部分站点无法直接抓取

`huggingface.co` 与 `r.jina.ai` 在命令环境里解析到保留地址，因此读不到 Hugging Face 的页面与文件清单。

**这一条需要用 Python 重新验证。** 第 10.1 节已确认 Python 一侧有出口，`danbooru.donmai.us` 与 `api.openverse.org` 都能访问，因此 `huggingface.co` 是否真的不可达尚未用 Python 复查。下次涉及模型下载时先用 Python 试一次，再决定是否需要请开发者代为查证。

### 10.5 PowerShell 脚本必须只用 ASCII 字符（已踩两次）

本机只有 Windows PowerShell 5.1。它读取**没有字节顺序标记**的脚本时按 ANSI 解码，脚本里的中文会损坏并直接导致语法报错。

第一次踩到时，解决办法是把脚本改成纯 ASCII，中文提示语外置到 `probe\messages.json`，由脚本以 UTF-8 显式读取。

第二次踩到的原因是编辑器类工具重写文件时会剥掉字节顺序标记。因此即使给脚本加回 BOM 也不可靠，**唯一稳妥的做法是脚本内一个非 ASCII 字符都不留**。

验证方法，非 ASCII 字节数必须为 0：

```
$bytes = [System.IO.File]::ReadAllBytes($path)
($bytes | Where-Object { $_ -gt 127 }).Count
```

### 10.7 Qt 在本环境无法建立 HTTPS 连接（重要）

**实测确认：Qt 的任何 HTTPS 请求都失败**，包括国内可直连的站点。明文 HTTP 可以通，说明不是网络不通，而是 TLS 层的问题。

Qt 用 Windows 安全通道做 TLS，运行时打印的 SSL 库版本为 `Secure Channel, Windows 10.0.26200`。请求失败的报错是 `UnknownNetworkError (No credentials)` 且 HTTP 状态码为空。这不代表缺少代理凭据，试过默认代理、不用代理、系统代理三种配置，结果完全一样。系统代理实际是 `127.0.0.1:7897`，但绕过它也不能解决问题。

同时 httpx 用自带的证书包，同一批地址下载完全正常，直连与走 7897 都成功。

**因此本项目的网络请求一律用 httpx，不要用 QtNetwork。** 缩略图加载已经按这个结论改成线程池加 httpx，见 `src/picfinder/ui/thumbnails.py`。这个改动是必要的，否则图墙上的缩略图会全部显示为加载失败。

### 10.8 QPixmap 只能在主线程创建

顺着 10.7 改缩略图加载时踩到的：工作线程里创建 QPixmap 会导致未定义行为。正确做法是工作线程只下载字节，通过信号把字节送回主线程，在主线程解码与转换。

Qt 的信号在跨线程时会自动使用队列连接，因此从工作线程发信号是安全的，接收者的槽会在主线程执行。

### 10.9 PowerShell 改写 Python 源文件会写入 BOM

PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会写入字节顺序标记。Python 读到带 BOM 的源文件会直接报 `SyntaxError: invalid non-printable character U+FEFF`。

本项目已踩过一次：用 `Set-Content` 批量替换一处字符串之后，构建脚本立刻无法运行。

避免用 PowerShell 改写 Python 源文件，优先用编辑工具。必须改时用不带 BOM 的写法：

```powershell
$text = [System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))
```

另外，`.NET` 的静态方法不认 PowerShell 的当前目录，路径必须用绝对路径。

### 10.10 测试不能用 tempfile

开发机的执行沙箱会重定向平台临时目录 `%TEMP%`。那个位置能建文件却删不掉，`tempfile.TemporaryDirectory()` 在创建或清理时报 `WinError 5 拒绝访问`。用它的用例会整片变红，看起来像代码坏了。

本项目已踩过一次：新写的路径层用例全部用了 `TemporaryDirectory`，报告里 14 条用例同时报错，第一反应是路径层有 bug，实际只是临时目录不可删。

需要临时目录时用项目内的 `tests/.scratch`，两种环境下都能创建与删除。见 `tests/test_paths.py` 的 `make_scratch`。

### 10.11 QLabel 开了自动换行会压掉长路径

路径里没有空格。`QLabel` 开了 `setWordWrap(True)` 之后，尺寸建议会把这种长串压成一列窄条，而版面只给一行高，结果只显示开头几个字符。实录：图库目录本该显示 `D:\WORK\DSHWorkplace\pic-finder\library`，界面上只出现 `D:`。

控件里的文字是对的，`text()` 取出来完全正确，所以这个错只在肉眼可见处出现。

避免办法是路径类标签一律不开自动换行。界面看不到时用 `work/shot_wizard.py` 截图核对，别靠读代码判断。

### 10.12 信号到信号必须直连，不能连到 `.emit`（重要）

```python
worker.one_done.connect(runner.one_done)          # 正确
worker.one_done.connect(runner.one_done.emit)     # 错误
```

写成 `.emit` 等于把信号当普通 Python 方法连。这样连了之后，从**第三个线程**发出的信号会被投递到工作线程自己的事件队列，而不是主线程的。等它转发到主线程时工作线程已经准备退出，事件被丢掉。

触发条件有两个，必须同时成立：发送方不是那个 QObject 所属的线程，且接收方在另一个线程。单元测试抓不到，因为测试里没有事件循环。因此这一类错误只在真机上出现。

实录：下载进度与单张结果从引擎内部的下载线程发出，图片全部下载成功、数据库全部写对，只有界面上的角标一个都不变、进度条不动。第一反应是去查路径推导与数据库写入，两者都是对的。隔离到最小复现后才发现，同样的结构里 `finished` 从工作线程发出能到达，而 `one_done` 从下载线程发出丢失。

**判断方法**：给引擎回调和界面槽各加一行日志。前者有输出而后者没有，就是这条。**修法**是把信号直连信号，一行改动。

### 10.13 打包入口不能直接指向包内的 `__main__.py`（重要）

PyInstaller 把入口脚本当**顶层脚本**执行，`__package__` 是空的。而 `picfinder/__main__.py` 用的是相对导入，于是打包产物一启动就报：

```
ImportError: attempted relative import with no known parent package
```

窗口模式下的表现是双击没有任何反应，或者弹一个带上面那行报错的窗口。开发期用 `python -m picfinder` 完全正常，因为 `-m` 会先建好包上下文。

想在不打包的情况下复现：`python src\picfinder\__main__.py --check`，立刻报同样的错。修法是加一个用绝对导入的启动器，见 `installer/entry.py`。

**这条例子的价值在于：第一次打包时它没有被发现。** 因为入口脚本在导入阶段就崩了，PyInstaller 的分析阶段根本没看到 `sqlite3`、`httpx`、`certifi` 这些依赖，结果第一次的产物比修好之后小了 5 MB，且「打包成功、文件齐全、体积正常」，一切指标看起来都对。

### 10.14 PyInstaller 不能在受限命令环境里运行

PyInstaller 发现钩子时要开一个内部管道与子进程通信。受限环境禁止开管道，报：

```
PermissionError: [WinError 5] 拒绝访问。
```

打包命令必须在放开管道的环境下执行。这不是项目代码的问题，是环境限制。

### 10.15 `Start-Process` 不会替你加引号

`Start-Process -ArgumentList` 把数组用空格拼成一条命令行，含空格的参数会被子进程拆成两个。

实录：验证脚本把中文检索词 `站姿 侧视` 传进去，程序收到两个参数，`argparse` 以**状态码 2** 退出，日志一个字的都没有写，看起来完全像打包坏了。实际上程序一行代码都没执行到。

`installer/verify.ps1` 里的 `Quote-Argument` 就是为这件事加的。**看到退出码 2 且日志为空，先怀疑参数被拆了。**

### 10.16 静默安装必须重定向输出

用 `Start-Process` 启动 Inno Setup 的安装程序，如果不重定向标准输出，安装程序在静默模式下写满继承来的管道后会卡住不动。

实录：不重定向时五分钟没有任何反应，目录一个文件都没建；加上 `-RedirectStandardOutput` 之后二十秒装完 224 个文件。

卸载程序同理。凡是「控制台程序在静默模式下会打印进度」的情形都要注意这一条。

### 10.17 匿名检索一次最多两个标签（重要）

Danbooru 匿名检索带三个及以上标签直接返回 **422 与 `PostQuery::TagLimitError`**。实测：1 与 2 个标签返回 200，3 与 4 个返回 422。

这个坑的代价很大。检索式的默认标签数原来是 3，于是**任何能翻出三个以上标签的中文输入都会当场失败**，而错误信息是一段 JSON，界面把它原样显示出来，用户只会以为软件坏了。用户实测反馈「第一版问题太多」，这一条是主因之一。

两条对策都已落地：默认标签数改成 2（`config.SearchDefaults.max_tags_in_query`），检索层把这段 422 翻成一句中文说明（`DanbooruClient._explain_error`）。

### 10.18 先看许可证再看数据

翻译词典要随程序分发，因此数据来源的许可证必须先确认。

实录：用户提供的那篇知乎文章介绍的 `DanbooruSearchOnline` 数据质量最高，但仓库是 GPL-3.0；同一需求下另有一个 MIT 许可、覆盖十万条标签的中文对照表，覆盖面已经够用，于是选了后者。

**流程：先查 LICENSE 与仓库描述里的 license 字段，再决定是否使用。** 数据一旦打进安装包就撤不回来了。

### 10.19 本机的 GitHub 与 HuggingFace 走代理，证书链校验会失败

`github.com`、`huggingface.co`、`raw.githubusercontent.com` 在本机解析到 `127.0.0.1`，即被代理接管。代理用自己的证书，因此 certifi 校验失败，报 `CERTIFICATE_VERIFY_FAILED`。

**这不等于不可达。** 关掉证书校验（`httpx.Client(verify=False)`）就能正常取到内容，实测 GitHub API 与 raw 文件都返回 200。

早前文档里写的「huggingface.co 不可达」是错的：那是代理拦截，不是站点故障。构建期的一次性抓取关掉校验可以接受，运行期的程序不做这件事。

### 10.20 安装程序原来需要管理员权限，已改成只做当前用户安装（重要）

`picfinder.iss` 里原来有 `PrivilegesRequiredOverridesAllowed=dialog`，向导会多出一页「选择安装模式」。开发者在这台机器上运行安装包时没有管理员权限，安装直接失败。

实录：2026-10-07 22:14，安装向导正常出现（搜狗输入法的日志证明窗口建起来了），选完目录点安装之后没有任何结果。`%LOCALAPPDATA%\Programs`、`C:\Program Files`、注册表卸载项三处都查不到痕迹。开启管理员权限之后，同一个安装包装成功了。

排查时先排除掉两个可能性。安装包本身没坏：在无沙箱环境下静默安装 229 个文件、写入卸载项、退出码 0。程序本身也没坏：装完之后 22:23:02 的日志显示词典与中文标签表都复制成功，97142 个标签的索引加载完成，Danbooru 源已启用。

真正的原因是安装模式页给出了一个需要提权的选项，而当前用户安装这条路径本来完全不需要管理员。对策是删掉 `PrivilegesRequiredOverridesAllowed=dialog`，只留 `PrivilegesRequired=lowest`。`{autopf}` 于是固定解析到 `%LOCALAPPDATA%\Programs`，永不提权。见 DD-25。

**顺带记住两件事。**

其一，Inno 的安装程序会把执行体自解压到 `%TEMP%\is-*.tmp`，再由那个副本继续干活。副本被外面的沙箱或杀毒软件挡掉时，表现就是「向导走到一半没了、没有任何错误、一个文件都没装」。判断方法是看 `%TEMP%\is-*.tmp` 里有没有那个副本。

其二，怀疑安装失败时，第一件事是加 `/LOG=<路径>` 重跑。Inno 会把每一步写进日志，比盯着界面猜快得多。

## 11. 写作与协作规范（必须遵守）

开发者要求所有项目文档遵守中文技术文档写作规范，规范原件位于：

`D:\WORK\DSHWorkplace\项目经验\中文技术文档的写作规范\`，以及经验总结 `D:\WORK\DSHWorkplace\项目经验\大肥鱼的技术文档写作规范_项目经验_20260929.txt`。

要点如下。

- **文件名**：不得含空格，只用半角字符，建议全小写，多词用连词线分隔。`README` 这类说明文件可用大写。
- **字间距**：全角中文与半角英文之间留一个半角空格；中文与半角数字之间的空格风格全文统一。
- **句子**：单句尽量 20 字以内，40 字以上不可接受。用简单句与并列句。
- **语态**：用主动语态，避免被动语态、双重否定、口语化表达。
- **标点**：中文用全角标点；中文句内并列词用顿号，即使并列词是英文；省略号用 `⋯⋯` 不用 `...`；句末括号加注时句号在括号外。
- **标题**：分四级，不跳级，避免同级只有一个标题，下级不与上级同名，慎用四级标题，并列内容改用项目列表。
- **数值**：千位以上加千分号；数值范围用 `～`；英文单位前留空格。
- **段落**：一段一个主题，中心句在段首，不超过 7 行。
- **引用**：引用第三方内容须注明出处并给出链接。

第四轮的两条经验值得记住。

其一，**`INSERT OR IGNORE` 会掩盖两类完全不同的问题**。重复写入属于正常，违反 CHECK 或外键属于错误，两者被一并吞掉之后，计数差额无法解释。正确做法是先按唯一键探测，再插入不带上 `IGNORE` 的语句，让真实错误浮出。

其二，**报告里的数字必须与库里的真实查询对账**。第四轮正是因为发现「应写入 379 行」与「表内 361 行」对不上，才找到 `common` 类别这个设计漏洞。只核对「脚本退出码为 0」会漏掉它。

第五轮修掉的两个实际缺陷值得记录。

其一，**接口端点猜错，导致批量核验全部误判**。核验脚本原先请求 `/tags/<名字>.json`，而 Danbooru 没有这个端点，该路径一律返回 404，于是 263 个标签被全部报为「不存在」。正确写法是 `/tags.json?search[name]=名字`。这个错误危险的地方在于它安静地给出了一整套看似可信的结论，如果当时选择相信它，会把词典里 263 个正确的标签全部删掉。

其二，**规范化顺序错误导致中文标点失效**。原先先做统一码 NFKC 规范化，再替换中文标点，而 NFKC 会把全角逗号先转成半角，之后按全角标点做的替换就找不到它，结果「站姿，侧身」变成「站姿,侧身」而不是「站姿 侧身」。修法是标点替换必须排在 NFKC 之前。

第五轮还有一条经验关于写测试：**测试失败时先怀疑测试自己的假设**。这一轮有两条用例连续失败，两次都是我对「某个标签是否存在」的假设错了（`standin` 与 `stand` 都是真实标签），而被验证的代码一直是对的。

第八轮修掉两个会静默出错的缺陷。

其一，**两级分级用两套尺度，导致结果被全部过滤**。配置层产出的是全名 `general` 与 `sensitive`，而站内返回的是单字母 `g` 与 `s`，比较时永远不相等，每一张图都被判为「分级越界」，界面显示零结果。这个缺陷是测试抓到的，不测的话第一次真实检索就是空结果，很容易误判为接口不通。修法是加一个显式换算函数，集中在类型模块一处定义。

其二，**Qt 在本环境连不上任何 HTTPS**。缩略图 196 张全部失败，报 `No credentials`。逐项排查后确认不是代理凭据问题，连国内站的 HTTPS 也不通，而明文 HTTP 正常。根因是 Qt 用 Windows 安全通道做 TLS 在此环境不可用，而 `httpx` 用自带证书包完全正常。修法是缩略图改用线程池加 `httpx`，顺带踩到 `QPixmap` 只能在主线程创建这一条。两条都记进第 10 节。

第十轮修掉一个只在真机上出现的缺陷，以及一个测试写出来才发现的漏洞。

第十一轮修掉的是一个「所有指标都正常但程序打不开」的缺陷。

打包入口最初直接指向 `picfinder/__main__.py`。PyInstaller 把它当顶层脚本执行，`__package__` 为空，相对导入当场失败，表现是双击没有任何反应。

**这个缺陷的危险之处在于它看起来完全成功**：打包退出码为零、程序目录生成、文件数与体积都正常、词典也正确打进包里。唯一不对劲的是它比修好之后小了 5 MB，因为入口在导入阶段就崩了，PyInstaller 的分析根本没看到 `sqlite3`、`httpx`、`certifi` 这些依赖。

抓到它靠的是验证脚本而不是打包脚本。第一次用调用运算符启动程序，`$LASTEXITCODE` 取到空值，一度以为程序正常退出，实际上窗口模式的程序不会让调用运算符等待，而它弹出的报错窗口一直开在那里。改用 `Start-Process -Wait -PassThru` 才拿到真实的退出状态。

第十一轮还踩到三个环境坑，都已记进第 10 节：PyInstaller 需要开管道因此不能在受限环境打包（10.14）；`Start-Process` 不替你加引号，中文检索词被拆开后 `argparse` 以状态码 2 退出、日志全空，看起来像打包坏了（10.15）；静默安装必须重定向输出，否则安装程序写满管道后不动（10.16）。

安装、运行、卸载三步已在本机完整演练：静默安装写入 224 个文件，运行后在程序目录旁生成 `data/` 与 `library/`，卸载后程序文件全部清除而这两个目录保留。后者是与 DD-07 原文的有意偏差，已登记为 OQ-21。

第十二轮修掉一个最贵的缺陷，以及一个只在并发下出现的缺陷。

其一，**匿名检索一次最多只能带两个标签**。检索式默认 3 个，于是任何翻出三个以上标签的中文输入都当场返回 422，界面把那段 JSON 原样显示给用户。这一条与词典太小叠加在一起，构成了用户「几乎没用」的完整体验。见第 10.17 节。

其二，**两个下载线程同时写同一个标签会撞唯一约束**。先查再插在单线程里没问题，并发下两边都查不到、两边都插，后插的失败，整张图被判下载失败；重试又撞上 post_key 的唯一约束，最终变成「跳过」。是测试套件里一条偶发失败把它暴露出来的，修法是 `ON CONFLICT DO NOTHING` 再回查，并补了一条八个任务共用三个标签的用例钉住它。

第十二轮还确认了一条早前写错的事实：**`huggingface.co` 不是不可达**，它被代理接管到 `127.0.0.1`，关掉证书校验就能访问。见第 10.19 节。

第十三轮没有改一行程序逻辑。它的价值在于**把一类失败从产品里删掉，而不是写进说明书**：模式选择页给出的「为所有用户安装」需要提权，而当前用户安装在功能上完全够用——程序的数据本来就要写在自己旁边。

排查过程值得记下来。开发者报故障时附了一份 `debug.log`，那是**搜狗输入法**写的，与安装包无关。但它意外地证明了一件事：安装向导的窗口确实建起来过（搜狗只在自己的输入框出现时才加载），时间戳也对得上。这条线索把范围从「安装包坏了」缩小到「向导走到某一步之后没了」。之后查遍三处安装痕迹、再在无沙箱环境下做对照安装，才定位到权限模式。

第十四轮最值得记的是那两条诊断结论，都是「用户描述的因果关系不成立，但现象真实」。

其一，**慢的原因不是单线程**。用户猜「检查是否只使用了单线程」。实际线程数是 6，而真正的开销是每张缩略图都新建一个 HTTP 客户端，于是每张图重做一次 TLS 握手。握手几十毫秒，缩略图只有一百多 KB，握手占的时间比传输还长。改成共用客户端之后快 16 倍——**如果照着用户的猜测把线程从 6 加到 24，只会让 24 个线程各自去做无效握手。**

其二，**「右侧一直无法显示图片」不是加载失败，是根本没往那儿摆**。两个图墙的列数都写死（检索页 6、图库页 5），而 `set_columns` 这个方法从头到尾没有任何地方调用过。改成按窗口可用宽度实时算之后，800 宽 3 列、1920 宽 9 列、2560 宽 12 列。

第十五轮又抓到一条同类的缺陷，值得与第十四轮那条并列记着：**只重写 `resizeEvent` 不足以跟上可用宽度的变化**。图墙自身没变大时，滚动区内部可用宽度照样会因为侧栏出现、滚动条消失而改变，而那种变化不触发图墙的 `resizeEvent`，列数就停在旧值上。修法是给滚动区的视口装事件过滤器。第十三轮那条「右侧空白」的修复只解决了「算得对」，这一条解决的是「算得及时」。

第十六轮最值得记的是**闪窗的根因**：`card.setParent(None)` 在 Qt 里等于把控件变成顶层窗口，Windows 会真的建一个原生窗口再隐藏，清一页 200 张卡片就闪 200 下。只能用 `hide()` 加 `deleteLater()`。这条在第十七轮改标签区时又用上了。

第十七轮的核心是 DD-31 那两万条词条。用户输入「真机伶」找不到赛马娘的角色，根因是词表用全角括号加限定词区分同名角色，规范化之后真正的键是「真机伶 赛马娘」，**不存在单独的「真机伶」**，而五档匹配没有一档覆盖「输入是某个键的前缀」这个方向。修法是建索引时额外注册短名入口，不碰数据文件。

这一轮踩到三个坑，都写进 DD-31 了，最值得记的是**注册顺序**：短名必须排在主译名与别名之后注册。反过来会先占住键，把真正的精确命中顶掉——当时所有候选都显示「精确档 1.00」，看起来完全正常，其实走的是短名档，分数虚高一档。

还纠正了交接文档里的一条事实错误：原文把 `curren_chan` 列为「能打中的输入」。实测打不中——索引里的键是 `curren_chan_(umamusume)`，`curren_chan` 这个键不存在，而片段档只从输入里切更短的片段，不会拿输入去前缀匹配更长的键。也就是说英文标签名同样缺「输入是键的前缀」这一档的方向，与中文那边是同一个缺口。这一轮没有动它（用户的阻塞项是中文名），留作已知问题。

### 调界面用的工具（第十三轮之后新增）

开发者在第十三轮提出想自己调界面，并选定「Designer 当草稿纸、不接入程序」的方式。工具都在 `work/ui_demo/`，用法见该目录的 `readme.md`。

| 文件 | 作用 |
|---|---|
| `dump_ui.py` | 启动一次真实界面，把控件树、文案、间距、对齐、下拉框候选项导成 `.ui`，同时存一张真实界面截图供对照 |
| `pages/*.ui` | 导出的草稿纸：检索页、图库页、设置页、单张结果卡片 |
| `run_demo.py` | 运行时加载任意 `.ui`，带 `--shot` 可存成图片 |
| `open-designer.bat` | 双击打开 Designer 并加载草稿纸 |

**改完界面代码之后必须重跑 `dump_ui.py`**，否则开发者手上的是旧草稿纸，他拖的是已经变样的界面。

导出有四条刻意偏差，写在 `dump_ui.py` 的模块说明里：隐藏控件会显示出来、缩略图显示「加载中」、检索之后才出现的控件没有、自定义控件退化成空白区域。

导出格式上有三处踩过的坑，改这个脚本时注意。其一，`.ui` 的 `item` **不支持** per-item 的 `stretch` 属性，uic 会直接报 `Unexpected attribute stretch`，拉伸要改用 `sizePolicy=Expanding` 表达。其二，`setFixedSize` 要同时导出最小与最大尺寸，只导最小尺寸会让固定尺寸的控件跟着布局乱变。其三，`QLabel` 的对齐方式不导出的话，`AlignCenter` 的文字会跑到左边去。
